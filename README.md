# Polymorph

A design system built as a **decision system**. Every design decision (a colour, a spacing
step, a focus ring, how a dialog enters) is made once, in the place that owns it. It is
referenced everywhere it applies, checked automatically, and safe to change.

Application code composes a closed vocabulary of components and binds content to it. It
cannot express a colour, a spacing value or an interaction mechanic, because those decisions
are already owned elsewhere. A redesign is therefore an edit to a few JSON files, not a sweep
across screens. An agent building UI with polymorph chooses from the vocabulary instead of
inventing one.

The vocabulary is one set of members, each specified once in `design/`. On the web, React, Vue,
Svelte, Solid and Angular draw it, and custom elements (`<poly-button>`) draw it on a page
written in HTML with no build. Two native renderers draw it: SwiftUI on iOS and Jetpack Compose
on Android. Every renderer reads the same tokens from the same theme engine,
and laws hold each one to the same specs.

```tsx
import { Button, ListPage } from '@polymorph/react-ui'

export function Inbox({ onNewTicket }: { onNewTicket: () => void }) {
  return (
    <ListPage
      title="Inbox"
      actions={<Button icon="add" label="New ticket" onClick={onNewTicket} />}
      emptyState={{ title: 'No tickets' }}
    >
      {/* rows… — no className, no style, no colours: those decisions are already made */}
    </ListPage>
  )
}
```

## How it fits together

- **A theme is a pairing** of a *system* (how the product is built: eight design axes and three
  fonts, in `design/systems/*.json`) and a *palette* (its colour seeds, in
  `design/palettes/*.json`). The theme engine turns a pairing into a law-checked set of tokens:
  `--pm-*` CSS custom properties for the web, and Swift, Kotlin and Dart values for the native
  packages. Light and dark are derived, not authored twice. Any palette works on any system, and
  a product can bring its own.
- **The vocabulary** is a closed set of members in seven tiers: structure, controls, overlays,
  layout, charts, the AI conversation tier and page archetypes. Every member has closed props,
  ships all of its states and transitions, and is styled only with tokens. `registry/system-card.md`
  lists them all.
- **Renderers.** React's members are written by hand on React Aria and Radix. The Vue, Svelte,
  Solid and Angular members are generated by `pnpm shells` from one framework-neutral
  description per member, on Zag state machines. The elements are generated as custom elements
  over the Solid members, in the light DOM, so they add no decision of their own. Every web
  renderer shares one CSS recipe per member (`@polymorph/recipes`). The SwiftUI and Compose members are written by hand against contracts
  generated from the registry, which is read from the same specs. The platform map
  (`design/platforms/`) says how each member renders on the web, iOS and Android, and the
  framework maps (`design/frameworks/`) say which members each generated web vocabulary ships.
- **Red rules** (ESLint and Stylelint rules) stop application code from expressing a design
  decision, in React and Solid TSX and in Vue, Svelte and Angular templates alike. They do not
  read an HTML page. When a product
  needs a one-off, the **exception ladder** gives it a declared, inventoried way to deviate.
- **Laws** (tests) check every claim: contrast for every pairing, coherence of every system,
  every member's states rendered and axe-clean in every web framework, every spec's behaviour
  contract run against every web renderer, every spec matching its code, and every native
  member token-only and complete.
- **For agents**, the registry describes the whole system in one generated file
  (`registry/system-card.md`), an MCP server exposes it as tools, and screens are written as
  validated JSON specs and emitted for any web framework, SwiftUI or Compose. A product can also
  draw a spec a model writes while it runs, as it streams in, with no build
  ([docs/run-time-screens.md](docs/run-time-screens.md)).

## Start

| You are building | Start with |
| --- | --- |
| a React app | `node <checkout>/packages/cli/bin/polymorph.js init my-app`, then `cd my-app && pnpm dev` |
| a Vue, Svelte, Solid or Angular app | the same command with `--framework vue`, `svelte`, `solid` or `angular` |
| a page in HTML: static, server-rendered, htmx or Turbo | the same command with `--framework elements`, which copies the files the page loads into its static directory ([docs/consuming.md](docs/consuming.md#a-page-with-no-build)) |
| an iOS app | the Swift package in `platforms/ios` as a path dependency: products `PolymorphTokens` and `PolymorphUI` |
| an Android app | the Gradle build in `platforms/android`, included with `includeBuild`: `dev.polymorph:tokens` and `dev.polymorph:ui` |
| a Flutter or Dart app | the tokens only, in `platforms/dart` (`polymorph_tokens`); there is no Flutter renderer |
| an existing web app | [docs/consuming.md](docs/consuming.md): the packages by hand, or members vendored with `polymorph add` |

`init` needs a checkout of this repository and a GitHub token that can read the packages
([docs/consuming.md](docs/consuming.md) has both, and a section per framework and platform).

## Working on polymorph

Node 24 (`.node-version`; `engines` requires ≥ 24) and pnpm 11 (`corepack enable` picks up the
pinned version).

```sh
pnpm install                              # also generates registry/ (the catalogue and system card)
pnpm exec playwright install chromium     # the browser test projects and pnpm proof drive a real browser

pnpm dev                                  # the workbench: studio, composer, components, Relay
pnpm dev:docs                             # the docs site
pnpm site                                 # the docs site as static HTML, in apps/docs/dist
```

There is no hosted CI, so the gates run where a change is made. Each platform has its own, and
the web has a second for Firefox and WebKit:

```sh
pnpm gate             # the web gate: typecheck, lint, inventory, test, coverage, builds, the site, size, the Next.js gate
pnpm gate:ios         # the SwiftUI members: contracts, laws, swift build and test, the audit (needs Xcode)
pnpm gate:android     # the Compose members: contracts, laws, the Gradle build and harness (needs a JDK; the wrapper fetches Gradle)
pnpm gate:engines     # the web gate's browser tests again, on Firefox and WebKit (needs pnpm exec playwright install firefox webkit)
```

The commands, by what they do:

| Command | What it does |
| --- | --- |
| `pnpm typecheck`, `pnpm lint`, `pnpm inventory`, `pnpm test`, `pnpm test:coverage` | the steps of `pnpm gate` ([docs/verification.md](docs/verification.md)) |
| `pnpm build`, `pnpm build:packages`, `pnpm size` | the apps' builds, the published packages' builds, and what a consumer ships against its budgets |
| `pnpm site` | the docs site written as static HTML into `apps/docs/dist`, which fails on a page that logs an error or links to a page the site does not have |
| `pnpm layout` | the layout measure over every member's gallery and the sample pages of the built workbench, at a phone's width and a desktop's |
| `pnpm registry` | regenerate `registry/` and the system card |
| `pnpm shells` | regenerate the Vue, Svelte, Solid and Angular members and the elements from their descriptions |
| `pnpm native:contracts` | regenerate the Swift and Kotlin contracts the native members conform to |
| `pnpm emit:native` | regenerate the native token packages' sources |
| `pnpm emit:examples` | regenerate the native example apps' screens from their specs |
| `pnpm emit <spec.json> [out]` | emit a screen spec for a web framework, SwiftUI or Compose |
| `pnpm emit:theme <system> <palette> [out.css]` | write one pairing's stylesheet, for review and handoff |
| `pnpm new:member <Name> --tier <tier>` | scaffold a member and every entry it needs ([CONTRIBUTING.md](CONTRIBUTING.md)) |
| `pnpm polymorph <command>`, `pnpm mcp` | the CLI and the MCP server, run from the checkout |
| `pnpm proof` | perform the system's guarantees against this repository and take screenshots |
| `pnpm eval`, `pnpm eval:report` | the agent eval, run by hand through the Messages API with a key or through a signed-in Claude Code, and its report |
| `pnpm changeset`, `pnpm version-packages`, `pnpm publish:packages` | record, version and publish a release ([CONTRIBUTING.md](CONTRIBUTING.md#releasing)) |

## The agent eval

[`eval/README.md`](eval/README.md) reports how often a model given only a screen brief and the
system's own tools produces a lawful screen, how often that screen has every part its brief
requires, how many `validate` calls it takes and what it costs. Each rate is printed with the
interval its number of runs supports. The page is generated from the recorded runs in
`eval/results/`. Producing the number is
the owner's step before a release, through either runner, which measure the same way:
`pnpm eval` sends the requests to the Messages API with `ANTHROPIC_API_KEY` set, and
`pnpm eval --runner cli` runs each brief through the owner's signed-in Claude Code, with no key
([docs/verification.md](docs/verification.md#the-agent-eval)).

## Status

The engine, the rules, the recipes, the run-time screen core, and a foundation and a vocabulary
for each web framework publish privately to GitHub Packages under the `metamorph-labs` org, and are installed under
their `@polymorph/*` names
([docs/consuming.md](docs/consuming.md#1-registry-access) has the table). The iOS, Android and
Dart packages are not published to a registry: an app reaches them through a checkout or a git
submodule of this repository, at a release tag. Polymorph is licensed under the MIT License
