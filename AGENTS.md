# Working in this repository

The operating guide for coding agents (and a fast orientation for people). Read
[docs/concepts.md](docs/concepts.md) before changing anything; it defines the words used here.

## What this is

Polymorph is a design system in which every design decision is made once, owned in one place
and checked by tests and lint rules. One vocabulary of members is specified in `design/` and
drawn by its renderers: React, Vue, Svelte, Solid and Angular on the web, custom elements for a
page written in HTML, SwiftUI on iOS and Jetpack Compose on Android.

- `design/` holds the decisions as data and specs, including the platform map
  (`design/platforms/`) and the framework maps (`design/frameworks/`).
- `packages/theme` turns a pairing into tokens; `packages/engine` is what a consumer installs on
  any web framework (the theme engine, laws, emitters, conventions, motion engine, chart engine,
  runtime and Vite plugin).
- `packages/recipes` holds each member's styling as framework-free CSS Modules, which every web
  renderer imports.
- `packages/react` and `packages/react-ui` are the React foundation and the React vocabulary,
  written by hand.
- `packages/{vue,svelte,solid,angular}` and `packages/{vue,svelte,solid,angular}-ui` are the
  other web foundations and vocabularies. The vocabularies are generated by `pnpm shells` from
  one description per member in `packages/shells/src/members/`.
- `packages/elements` and `packages/elements-ui` are the elements foundation and vocabulary: each
  member as a `poly-*` custom element in the light DOM that renders its generated Solid member, so
  the elements are a distribution of the Solid rendering and add no decision of their own.
  `pnpm shells` writes their definitions and fixtures, and no anatomy.
- `platforms/ios` (`PolymorphTokens`, `PolymorphUI`) and `platforms/android` (`:tokens`, `:ui`)
  are the native packages: SwiftUI and Compose members written by hand against contracts
  `packages/native` generates. `platforms/dart` holds the tokens only.
- `packages/rules` holds the red rules that stop application code from making design decisions.
- `packages/screen` is the run-time core for a screen a model writes and a host draws with no
  build: the check, the streaming reader, the walk and the run-time card, which
  `@polymorph/react/screen` and `<poly-screen>` (`@polymorph/elements-ui/screen`) draw from.

[docs/architecture.md](docs/architecture.md) maps every package and platform.

## Commands

```sh
pnpm install                 # also runs `pnpm registry` (prepare)
pnpm typecheck               # all packages and apps
pnpm lint                    # eslint (incl. red rules) + stylelint + prettier
pnpm test                    # vitest: logic (node) + the browser projects (real chromium)
pnpm exec vitest run <path>  # a subset — a file, a directory, or --project <name>
pnpm test:coverage           # coverage thresholds; they only ever go up
pnpm gate                    # the web gate: typecheck, lint, inventory, test, coverage, builds, the site, size, the static-page check, the Next.js gate
pnpm gate:ios                # the iOS gate: contracts, examples, native laws, swift build/test, audit (Xcode)
pnpm gate:android            # the Android gate: contracts, examples, Kotlin laws, Gradle build and harness (JDK)
pnpm gate:engines            # the Firefox and WebKit gate: the browser projects and the static-page check again, on both engines
pnpm gate:next               # the Next.js gate by itself: an App Router app built from the published builds (--no-build, or a stage)
pnpm gate:no-build           # the static-page check: the elements' no-build files on a plain page, three engines (--no-build, or an engine)
pnpm inventory               # declared exceptions; non-zero on an undeclared one
pnpm registry                # regenerate registry/ and the system card
pnpm shells                  # regenerate the Vue, Svelte, Solid and Angular members and the elements from their descriptions
pnpm native:contracts        # regenerate the Swift and Kotlin contracts (--check: fail if stale)
pnpm emit:native             # regenerate the native token sources (--check: fail if stale)
pnpm emit:examples           # regenerate the native example screens from their specs (--check)
pnpm emit <spec.json> [out]  # emit a screen for a web framework, SwiftUI or Compose
pnpm build:packages          # the published builds of the engine, rules, the run-time core, react and each framework's packages
pnpm size                    # what a consumer ships, against budgets, a page with no build included (needs build:packages; --why)
pnpm layout                  # the layout measure over every gallery and sample page, at two widths (needs build)
pnpm new:member <Name> --tier <tier>   # scaffold a new member and every entry it needs (see CONTRIBUTING.md)
pnpm eval                    # the agent eval against a real model: ANTHROPIC_API_KEY, or --runner cli with Claude Code signed in (--claude <path> for another CLI; --mode runtime for the run-time lane); costs money or plan usage
pnpm dev / pnpm dev:docs     # the workbench / the docs site
pnpm site                    # the docs site as static HTML for a static host; fails on a page error or a dead link (--no-build)
```

A change is done when the gate for what it touches passes. `pnpm gate` is the web gate:
typecheck, lint, inventory, the suite, coverage, the apps' builds, the docs site written as
static pages, which fails on a page error or a dead link, the layout scan of the workbench's pages, the packages' builds, the size budgets, the static-page check, which loads the
elements' no-build files into a page served as plain files on Chromium, and the Next.js gate,
which builds an App Router application from the published React builds. A change to `platforms/ios` or to what
the iOS contracts are generated from also needs `pnpm gate:ios`, and one to `platforms/android`
or the Kotlin contracts `pnpm gate:android`. A change to a member, a recipe, a foundation or a
browser test also needs `pnpm gate:engines`, which repeats the browser projects, and the
static-page check, on Firefox and WebKit. There is no hosted CI, so these are the check. Browser tests need
`pnpm exec playwright install chromium` once, and the engines gate
`pnpm exec playwright install firefox webkit`.

## Before you build anything

- **Read the system card.** `registry/system-card.md` (regenerate with `pnpm registry`) lists
  every member, its props, the token families, the rules, and what each framework and platform
  renders. Check whether what you need already exists before adding anything.
- **Read one member end to end** before writing one: its spec in `design/components/`, the
  React component, its `*.module.css` recipe in `packages/recipes/src`, its `*.states.tsx`
  states fixture, its test, its description in `packages/shells/src/members/`, and its SwiftUI
  and Compose files (`platforms/ios/Sources/PolymorphUI/`,
  `platforms/android/ui/src/main/kotlin/dev/polymorph/ui/`).

## Rules that will stop you

- **Application code** (`apps/**`, except `apps/*/src/harness/**`) composes members and binds
  content. No CSS files, no `style`/`className` on members, no raw `<button>`/`<input>`, no
  colours or lengths, no motion libraries, no icon imports. The same rules read Vue
  single-file components, Svelte components, Solid TSX and Angular templates in an app that
  uses those frameworks. [docs/rules.md](docs/rules.md) has the full list.
- **Member CSS** is a recipe in `packages/recipes/src/<tier>/`, at the path its member has in
  `packages/react-ui/src`, and the member imports it as
  `@polymorph/recipes/<tier>/<file>.module.css`. It expresses design values only through `--pm-*`
  tokens, and every token it reads must exist. No vocabulary package holds a stylesheet of its
  own.
- **Member code stays vendorable.** A file in `packages/react-ui` imports `@polymorph/react`,
  `@polymorph/react/motion`, its own siblings and its recipe, so `polymorph add` can copy it into
  another repository. It never imports `@polymorph/theme`, `@polymorph/rules`, `@polymorph/registry`, the
  vocabulary package itself or a tool package (`vendorable-imports`). It does not import `@polymorph/engine` either: it reaches the engine
  through `@polymorph/react`, and `packages/react-ui` lists the engine only as a dev dependency,
  for its tests. A vendored copy may import `@polymorph/engine`, which the rule allows.
- **Generated members are changed through their description.** A Vue, Svelte, Solid or Angular
  member, and an element, is written by `pnpm shells` from `packages/shells/src/members/<member>.ts`.
  Change the description or the renderer (`packages/shells/src/{vue,svelte,solid,angular,elements}.ts`),
  then run `pnpm shells`; the freshness law fails on any generated file that differs.
- **The elements render the Solid members.** A change to `packages/solid` or `packages/solid-ui`
  reaches every page that uses the elements, so run the `elements` project with the `solid` one;
  its parity law fails where an element renders a document other than its Solid member's. The red
  rules do not read HTML, so nothing lints an elements page.
- **Native members are held to their contracts.** A SwiftUI or Compose member conforms to its
  generated `PM<Member>Rendering`, reads every value from the theme, writes no text a person
  reads, and imports only what its laws allow ([docs/native.md](docs/native.md),
  [docs/verification.md](docs/verification.md)).
- **Never silence a red rule with `eslint-disable`.** `pnpm inventory` fails on it. If a
  deviation is genuinely needed, climb the
  [exception ladder](docs/rules.md#the-exception-ladder): variant → `DensityScope`/`ToneScope`
  → `patch` prop → `<Bespoke>` zone → promote into the vocabulary.
- **Some violations fix themselves.** `pnpm exec eslint --fix <path>` rewrites the ones with
  exactly one lawful answer — a `className` on a member, a bare icon import the role map names,
  a text-only `<button>` ([docs/rules.md](docs/rules.md#what-the-rules-fix)). What it leaves
  reported is a decision: climb the ladder.
- **A law that fails is a decision the system already made.** Satisfy it, or change the
  decision where it is owned — never weaken the test to get green.
- Accessibility laws are never suspended, anywhere.

## Things that are easy to get wrong

- **Specs are parsed.** `design/components/*.md` and `design/archetypes/*.md` are read by
  `packages/registry/src/vocabulary.ts` and the spec-staleness law
  (`packages/rules/src/spec-api.ts`). A prop the code has and the spec lacks — or the reverse —
  fails the suite. Keep their tables and fences in shape. A spec's `contract` fence is parsed
  too, and the conformance law runs every statement in it against every web renderer
  ([docs/conformance.md](docs/conformance.md)). So is the `agent` fence of a spec's `## Agent`
  section: `pnpm registry` fails on a fault in it, the staleness law
  (`packages/registry/src/agent-staleness.ts`) holds the React member's `useAgentMember` call
  and the description's `agent` block to it, and the conformance law runs every statement with
  an agent bridge installed ([docs/agents.md](docs/agents.md)).
- **The ladder is parsed** from [docs/rules.md](docs/rules.md) by
  `packages/registry/src/rulings.ts`. Keep that section's shape.
- **Generated files are never hand-edited.** Each says what writes it in its header:
  - `registry/`, `apps/*/src/fonts.gen.ts` and `packages/screen/src/vocabulary.gen.ts`:
    `pnpm registry`, after adding a member or changing which tokens a member reads.
  - The Vue, Svelte, Solid and Angular members, their states fixtures, indexes and galleries,
    and each foundation's `Icon` and glyph data, and the elements' definition modules, fixtures,
    index, galleries, `definitions.ts` and `poly-icon`: `pnpm shells`.
  - The native contracts, `platforms/ios/Sources/PolymorphUI/Generated/` and
    `platforms/android/ui/src/generated/`: `pnpm native:contracts`.
  - The native token sources, `platforms/ios/Sources/PolymorphTokens/Generated/`,
    `platforms/android/tokens/src/generated/` and `platforms/dart/lib/src/generated/`:
    `pnpm emit:native`.
  - The native example screens (`InboxView.swift`, `NewTicketView.swift`, `InboxScreen.kt`):
    `pnpm emit:examples`.
- **Other repositories install these packages** (`@polymorph/engine`, `@polymorph/rules`,
  `@polymorph/recipes`, and the React, Vue, Svelte, Solid, Angular and elements foundations and
  vocabularies, from GitHub Packages), copy the elements' no-build files with
  `polymorph init --framework elements`, and reach `platforms/` through a checkout. A renamed
  export, a newly required prop or a layout change is a major release for all of them; prefer
  additive, optional changes, and add a changeset for anything a consumer sees
  (`.changeset/README.md`). `packages/react-ui/consumption.test.ts` and the packages' `packaging.test.ts`
  files pin the entry points.
- **The published build is not the source.** `exports` points at `src/`; `publishConfig.exports`
  points at `dist/`, built by `pnpm build:packages`. Releasing is in CONTRIBUTING.md:
  `pnpm publish:packages` runs the gate before it uploads. Never publish from a dirty tree, and
  never by hand. The elements vocabulary's build also writes `dist/cdn/`, the files a page with no
  build loads (`polymorph.js`, its chunks, `polymorph-all.js`, `polymorph.css`, the theme sheets,
  `prepaint.js`), which `polymorph init --framework elements` copies and `pnpm gate:no-build`
  loads; it compiles the Solid members with their recipes through the reach-through transform,
  for a bundler as for the page.
- **Size budgets are ceilings, not targets.** `pnpm size` measures the published builds in
  fixture apps (`scripts/size/`), and a page with no build from `dist/cdn/`, file by file. Over budget means something heavy reached a consumer's bundle:
  find it with `pnpm size --why` before raising a ceiling, and raise one only with its reason in
  the same commit.
- **Wiring lists.** A new member must appear in four hand-written lists, in the three platform
  files (`design/platforms/{web,ios,android}.json`), in every framework map
  (`design/frameworks/{vue,svelte,solid,angular,elements}.json`) and, while it has no SwiftUI or Compose
  rendering, in the two pending lists (`packages/native/src/pending.ts`, `kotlin-pending.ts`) with the
  counts their laws pin. It also needs a description in `packages/shells/src/members/`.
  `pnpm new:member` writes all of them, with a `DECIDE` placeholder in each phone file and each
  framework map that the laws refuse until the author decides from the spec.
  `packages/react-ui/src/wiring.test.ts` reds when one of the four lists is missing the member;
  the platform law (`packages/registry/src/platforms.test.ts`), the framework law
  (`packages/registry/src/frameworks.test.ts`), each generated vocabulary's map law and the
  native conformance laws red on the rest.
- **Browser tests and focus.** Component tests run in real chromium. Code that focuses an
  element must not race the framework's commit; tests that read `document.activeElement` after
  an overlay closes should wait (`vi.waitFor`), because Radix and Zag restore focus
  asynchronously. A test that fails only under full-suite load is usually this kind of race.
- **Firefox and WebKit.** A test may not branch on the engine to pass. It may only declare a
  skip on a limit of the test tooling, and `packages/conformance/src/engines.ts` names each
  limit. A test that fails on one engine only is usually acting before the member has settled:
  a Zag machine focuses its panel or field a frame after it opens. A test that states words in
  a language names its locale, because Firefox and WebKit take the machine's.

## Writing comments, docs and tests

- **Plain register.** One idea per sentence, the fact first and the reason after. No metaphor,
  aphorism, personification or rhetorical repetition: a reader must be able to tell a load-bearing
  sentence from a decorative one, so there are no decorative ones. Delete any sentence that carries
  no fact or reason.
- Describe what is true now and why, in present tense. A comment that explains why the code
  is not the obvious alternative is valuable; a comment that narrates history is not.
- No plan or ticket identifiers, phase names, or dates of past decisions in code, tests or
  docs. A test fails if they appear (`packages/rules/src/plan-references.test.ts`).
- Plans, proposals and follow-ups go in GitHub issues, not in the repository.
- Link docs by file (`docs/rules.md`), not by section number.
- A count in a doc (members, frameworks, laws) is computed from the tree or left out.
- Use the terms in the [glossary](docs/concepts.md#glossary): member, tier, system, palette,
  pairing, red rule, law, states fixture, description, renderer, foundation, platform map,
  framework map, contract.
