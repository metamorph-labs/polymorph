# Rules

Polymorph enforces its design claims by machine, not by review. This page covers the lint part of
that enforcement: the **red rules**, the ladder of declared exceptions that answers them, and the
inventory that lists every exception.

Terms used on this page:

- **Vocabulary**: the closed set of components polymorph ships. On the web each framework has its
  own package of members (`@polymorph/react-ui`, `@polymorph/vue-ui`, `@polymorph/svelte-ui`,
  `@polymorph/solid-ui`, `@polymorph/angular-ui`), with the icon gateway and motion presence in its
  foundation (`@polymorph/react`, `@polymorph/vue`, …) and the motion engine and conventions in
  `@polymorph/engine`. A **member** is one component in it. See [concepts.md](concepts.md). The red
  rules govern web code. The SwiftUI and Compose members are held by their own laws
  ([native.md](native.md)).
- **Red rule**: an ESLint or Stylelint rule that fails the gate.
- **Law**: a test that enforces a design claim. [verification.md](verification.md) covers the test
  suite. The laws a contributor meets are summarised [below](#laws-that-behave-like-rules).
- **Recipe**: a member's CSS module, such as `packages/recipes/src/controls/button.module.css`.

## Two halves

The rules govern two kinds of code, written by different people, and they require different things
of each:

| Half | What it is | What the rules require | When the rules say no |
| --- | --- | --- | --- |
| **Application code** | screens: `apps/**` in this repository, your own `src/` in a consumer | compose the vocabulary and bind content; express no style, rebuild no control, reach past no gateway | climb the [exception ladder](#the-exception-ladder) |
| **The vocabulary** | component source in `packages/react-ui`, recipes in `packages/recipes`, and the icon gateway and motion presence in `packages/react` here, the vendored directory in a consumer | spell every design value as a `--pm-*` token, never branch on which theme is active; `packages/react-ui` stays copyable into another repository, where its copies import the installed `@polymorph/react` and `@polymorph/engine` | fix the code; there is no rung |

The vocabulary has no ladder, because exceptions are taken *from* it. A `<Bespoke>` zone inside a
component would defeat the component's purpose.

The Vue, Svelte, Solid and Angular vocabularies (`packages/{vue,svelte,solid,angular}-ui`) are
generated by `pnpm shells` from one description per member, and their members import the same
recipes. The red rules do not lint the generated files. Their laws do
([below](#laws-that-behave-like-rules)), and `packages/shells/src/shells.test.ts` holds them to what
the generator writes. The elements (`packages/elements-ui`) are generated the same way, over the
Solid members.

The red rules read TSX, Vue and Svelte components and Angular templates. They do not read an HTML
page, so an app that writes the elements in HTML has no rule that checks its pages: `verify` and
the MCP tool `validate` answer such a page with a fatal result that says so, and `polymorph check`
leaves it unread with a note. A script beside the page is read as any TypeScript is.

## The ESLint rules

Plugin name `polymorph`. Source in `packages/rules/src/rules/`. Every rule is syntactic: it reads
TSX, a Vue template ([below](#in-a-vue-template)), Svelte markup ([below](#in-a-svelte-file)), an
Angular template ([below](#in-an-angular-component)) and import specifiers and never queries the
type checker. Solid TSX is TSX ([below](#in-solid-tsx)).

| Rule | What it forbids | Half | Rungs that answer it |
| --- | --- | --- | --- |
| `polymorph/no-raw-styles` | a `style` or `css` prop; a `className` on a vocabulary component or a plain element; a colour (`#hex`, `rgb()`, `oklch()`, …) or length (`px`, `rem`, `em`) written in a string; a colour in any syntax in a `style` a `<ThirdParty>` boundary lifts, and a `style` there whose property names are not written out; a `<ThirdParty>` boundary that hosts nothing | application | 1, 3, 4 |
| `polymorph/no-app-css` | importing or re-exporting a stylesheet (`.css`, `.scss`, `.sass`, `.less`, `.styl`) from anywhere but `@polymorph/`, `@fontsource*/` and a library the file hosts in a `<ThirdParty>` boundary | application | 1, 4 |
| `polymorph/no-raw-interactive` | `<button>`, `<input>`, `<select>`, `<textarea>`, `<option>`, `<optgroup>`; a click, key or pointer handler on a plain element such as `<div>`, `<a>` or `<li>` | application | 1, 4 |
| `polymorph/no-external-motion` | importing a motion library (`motion`, `framer-motion`, `react-spring`, `gsap`, `react-transition-group`, …) | application | 1, 4 |
| `polymorph/no-external-icons` | importing an icon set (`lucide`, `lucide-react`, `react-icons`, `@heroicons/react`, … or any package named for `icon` or `icons`); an inline `<svg>` | application | 1, 4, 5 |
| `polymorph/no-external-dataviz` | importing a chart library (`recharts`, `chart.js`, `echarts`, `highcharts`, …) or any `d3-*`, `@visx/*`, `@nivo/*` package | application | 1, 4 |
| `polymorph/scoped-token-owners` | naming a pattern-scoped token (`--pm-shell-*`, `--pm-page-*`, `--pm-chart-height-*`) in a file that does not own the pattern | application | none |
| `polymorph/one-opener` | one module that renders both `<PageHeader>` and `<Hero>` — each renders the page's `<h1>`, so the pair puts two on the page | application | 1 |
| `polymorph/vendorable-imports` | in vendored component source: a relative import that leaves the vendored tree, a deep `@polymorph/<pkg>/src/…` import, or an import of `@polymorph/theme`, `@polymorph/rules`, `@polymorph/registry`, `@polymorph/react-ui`, `@polymorph/spec`, `@polymorph/cli` or `@polymorph/mcp` (another member is imported by relative path). The published surfaces of `@polymorph/engine` and `@polymorph/react` are allowed, because a consumer installs them | vocabulary | none |

Three of the application rules have a second use in this repository. `eslint.config.ts` also applies
`no-external-icons`, `no-external-motion` and `no-external-dataviz` to
`packages/{engine,react,react-ui}`, each with an `allowIn` list that names one gateway. The icon set
(`lucide`) is confined to the role map `packages/react/src/icon/map.tsx` and its test. A motion
library could enter only `packages/engine/src/motion/`, which imports none, because the engine runs
on the browser's Web Animations API. The borrowed scale arithmetic is confined to the chart engine.
The gateways are named in `packages/rules/src/containment.ts`.

### In a Vue template

The ESLint rules read a Vue single-file component as they read TSX. Under `vue-eslint-parser`,
which a Vue app's config sets for `.vue` files ([frameworks.md](frameworks.md)), a component's
`<script setup>` is the program the rules walk, and its template is a second tree they walk
through the parser's services. The rules never import the parser, so a React app needs nothing
from Vue. `@polymorph/rules` names it as an optional peer, and `verify` loads it only to read a
`.vue` file. The reports are the same sentences with the same answers, and an answer computed from
what was written is in template syntax: `<Inline :gap="4">` where a TSX report says
`<Inline gap={4}>`, and `@click` for `onClick`. A rule's fixed sentence is written once, as JSX:
a raw `<option>` is answered with `<Select options={…}>` in either file.

| Rule | What it reads in a template | Example |
| --- | --- | --- |
| `no-raw-styles` | `class` or `style`, static or bound (`:class`, `:style`): on a member it is removed, because a Vue member inherits neither. A `class` on a plain element and a `style` on anything that is not a member (a plain element, another library's component) are reported with what they read as; a `class` on another library's component is its own. A raw colour or length in a bound expression or a static attribute | `<Button class="wide" label="Go" />` → `<Button label="Go" />` |
| `no-raw-interactive` | a raw `<button>`, `<input>`, `<select>`, `<textarea>`, `<option>` or `<optgroup>`; a listener (`@click`, `v-on:keydown`) on a plain element. Nothing is rewritten, because the three fixes write TSX | ``Unexpected `@click` on <div>. A clickable <div> has no control's states or keyboard path: use `<Button variant="ghost" label="…">` (rung 1), …`` |
| `no-app-css` | a `<style>` block, read for what its rules become; a `<style src>` as an import of its file | ``Unexpected <style> block. Its rules are `<Inline :gap="4" :p="5">` (rung 1), so the block can go.`` |
| `no-external-icons` | an inline `<svg>`; an import of `lucide-vue-next`, `@heroicons/vue`, `@iconify/vue` or `vue-feather`, whose glyphs read as roles. Nothing is rewritten, because the glyphs are used in the template | ``Unexpected icon import `lucide-vue-next`. `Trash2` is `<Icon name="delete" />` (rung 1). …`` |
| `no-external-motion` | an import of `motion-v` or `@vueuse/motion`; Vue's own `<Transition>` and `<TransitionGroup>`, an entrance written at a call site | ``Unexpected <Transition>. It is an entrance and exit: `<Dialog>`, `<Drawer>`, `<Popover>` and `<Toast>` animate their own (rung 1). …`` |
| `no-external-dataviz` | an import of `vue-chartjs`, `vue-echarts`, `vue3-apexcharts`, `highcharts-vue` or `@unovis/vue` | ``Unexpected charting import `vue-chartjs`. `Bar` is `<BarChart :data="…" :series="…">` (rung 1). …`` |
| `one-opener` | `<PageHeader>` and `<Hero>` in one template | ``Unexpected <Hero> beside <PageHeader>: …`` |

A tag is read as the member a `<script setup>` imports, as Vue's compiler resolves it. A
kebab-case tag is read in PascalCase: `<data-table>` is `DataTable`. A lowercase tag that is not an
HTML, SVG or MathML element is read capitalised when the script imports that name: `<card>` is the
`Card` it imports. `<button>` is the HTML element even where `Button` is imported, as Vue renders
it. A `<Bespoke>` (or a `<bespoke>` where `Bespoke` is imported) lifts what it lifts in TSX, and a
file that declares one is exempt from the import bans. `messages.test.ts` holds the Vue reports to the
same standard as the TSX ones, `packages/rules/src/rules/vue.test.ts` runs each rule under the Vue
parser, and `packages/rules/fixtures/vue/` holds a violating, a lawful and a zoned component.

### In a Svelte file

The ESLint rules read a Svelte component as they read TSX. A Svelte app's config parses `.svelte`
files with `svelte-eslint-parser`, which reads a `<script lang="ts">` and the markup's expressions
with the TSX parser. Unlike a Vue template, the markup is part of the program the rules walk: the
rules read a script's imports where TSX has them, and visit the markup's elements, attributes and
directives directly. The rules never import the parser. `@polymorph/rules` names it as an optional
peer, and `verify` loads it only to read a `.svelte` file. The reports are the same sentences with
the same answers. An answer is written as JSX writes it, because a Svelte member takes each prop
under its React name: `<Inline gap={4}>`, `onClick={save}`. Nothing in a `.svelte` file is
rewritten except a `class` or `style` removed from a member, because the other fixes rewrite JSX.

| Rule | What it reads in a component | Example |
| --- | --- | --- |
| `no-raw-styles` | `class` or `style`, static, in braces or shorthand (`{class}`): on a member it is removed, because a member ignores a prop it does not declare. A `class` on a plain element and a `style` on anything that is not a member are reported with what they read as. A `class:active` directive on a plain element and a `style:padding` directive are reported the same way. A raw colour or length in a static attribute (`<Stack gap="12px">`) or an expression | ``Unexpected `style:padding` on <div>. `padding` is `<Stack p={4}>` (rung 1).`` |
| `no-raw-interactive` | a raw `<button>`, `<input>`, `<select>`, `<textarea>`, `<option>` or `<optgroup>`; an event attribute (`onclick`) or an `on:click` directive on a plain element. Options written by `{#each}` are not counted | ``Unexpected `onclick` on <div>. A clickable <div> has no control's states or keyboard path: use `<Button variant="ghost" label="…">` (rung 1), …`` |
| `no-app-css` | a `<style>` block, read for what its rules become | ``Unexpected <style> block. Its rules are `<Inline gap={4}>` (rung 1), so the block can go.`` |
| `no-external-icons` | an inline `<svg>`; an import of `lucide-svelte`, `@lucide/svelte`, `svelte-heros`, `svelte-heros-v2`, `phosphor-svelte`, `@iconify/svelte` or an unplugin-icons module (`~icons/…`). The lucide glyphs read as roles | ``Unexpected icon import `lucide-svelte`. `Trash2` is `<Icon name="delete" />` (rung 1). …`` |
| `no-external-motion` | an import of `svelte/transition`, `svelte/animate`, `svelte/motion`, `svelte/easing`, `svelte-motion` or `@humanspeak/svelte-motion`; a `transition:`, `in:`, `out:` or `animate:` directive on any element, read by its function: `slide` is a section opening and closing, `fade`, `fly`, `scale`, `blur`, `draw`, `crossfade`, `send` and `receive` an entrance and exit, and any other (`animate:flip`) a zone | ``Unexpected `transition:fade` on <div>. It is an entrance and exit: `<Dialog>`, `<Drawer>`, `<Popover>` and `<Toast>` animate their own (rung 1). …`` |
| `no-external-dataviz` | an import of `layerchart`, `svelte-chartjs`, `svelte-apexcharts`, `svelte-frappe-charts`, `@carbon/charts-svelte` or any `@unovis/*` package | ``Unexpected charting import `layerchart`. `BarChart` is `<BarChart data={…} series={…}>` (rung 1). …`` |
| `scoped-token-owners` | a pattern-scoped token in a static attribute, as in a string | ``"--pm-shell-*" belongs to app-shell.module.css and 1 more, not this file (…).`` |
| `one-opener` | `<PageHeader>` and `<Hero>` in one component | ``Unexpected <Hero> beside <PageHeader>: …`` |

A tag is read as Svelte reads it. A capitalised or dotted tag (`<Tabs.Content>`) is a component, a
lowercase tag is an HTML element, and a tag with a hyphen is a custom element, which is another
library's component. A member is a component a script imports from a vocabulary module, whether the
script comes before the markup or after it. A `<Bespoke>` lifts what it lifts in TSX, a directive
included, and a file that declares one is exempt from the import bans.
`packages/rules/src/rules/svelte.test.ts` runs each rule under the Svelte parser,
`messages.test.ts` holds the Svelte reports to the same standard as the TSX ones, and
`packages/rules/fixtures/svelte/` holds a violating, a lawful and a zoned component.

### In Solid TSX

Solid writes JSX, so the rules read a Solid file with the TSX parser, as they read React. A file is
Solid when the config's settings say so (`settings: { polymorph: { framework: 'solid' } }`,
exported as `solidSettings`) or when it imports `solid-js` (or a subpath of it), `@polymorph/solid`
or `@polymorph/solid-ui`. Any other TSX file is read as React. `verify` reads a fragment as Solid
when it is given `framework: 'solid'`, which also makes `@polymorph/solid-ui` the module its fixes
import from. `class`, `classList`, a handler written in lowercase and a listener directive are read
this way only in a Solid file, so a React file reads as React.

| Rule | What it reads in Solid | Example |
| --- | --- | --- |
| `no-raw-styles` | `class` and `classList`, as `className` is: on a member it is removed, and on a plain element it is reported with what it reads as, a `classList` object by its keys. A `style` string (`style="padding: 12px"`) is read declaration by declaration, and a style object's kebab-case keys (`'padding-top'`) as the CSS properties they are | ``Unexpected `classList` on <div>. `flex gap-2 p-4` reads as `<Inline gap={3} p={5}>` (rung 1). …`` |
| `no-raw-interactive` | a handler as written: `onClick`, `onclick`, `on:click` or `oncapture:click`. The three fixes run when `vocabulary` is set, and `fixableSolidControls` sets it to `@polymorph/solid-ui`. A `<label for="…">` names its checkbox as `htmlFor` does. A `<textarea>` is not rewritten, because its `onChange` in Solid is the native change event, and `Textarea` calls its `onChange` on every input | ``Unexpected `on:click` on <li>. A clickable <li> has no control's states or keyboard path: …`` |
| `no-external-icons` | an import of `lucide-solid`, `@lucide/solid` or `solid-heroicons`. An import from `lucide-solid` is fixed as `lucide-react` is in React: `Icon` is imported from `@polymorph/solid`, or added to an existing import of `@polymorph/solid-ui` or `@polymorph/solid`. An import from `lucide-react` in a Solid file is reported and not rewritten | `<Trash2 />` from `lucide-solid` → `<Icon name="delete" />` |
| `no-external-motion` | an import of `solid-motionone`, `@motionone/solid`, `solid-transition-group` or `@solid-primitives/transition-group`. `<Motion.div>`, `<Presence>` and `<Transition>` are read as their React counterparts are | ``Unexpected motion library `solid-motionone`. `Motion.div` animating opacity is an entrance and exit: … (rung 1).`` |
| `no-external-dataviz` | an import of `solid-chartjs`, `solid-apexcharts` or any `@unovis/*` package | ``Unexpected charting import `solid-chartjs`. `Line` is `<LineChart data={…} series={…}>` (rung 1). …`` |

`no-app-css`, `scoped-token-owners` and `one-opener` read Solid as they read React.
`packages/rules/src/rules/solid.test.ts` runs each rule with the Solid settings, `messages.test.ts`
holds the Solid reports to the same standard, and `packages/rules/fixtures/solid/` holds a
violating, a lawful and a zoned screen.

### In an Angular component

An Angular component is a TypeScript module whose `@Component` holds its template, inline or in a
`templateUrl` file. The rules read the module with the TSX parser, as any `.ts` file, and the
template with `@angular-eslint/template-parser`: an external template as the `.html` file it is, and
an inline one through the processor of `@angular-eslint/eslint-plugin-template`, which extracts each
`template:` into a virtual `.html` file and maps its reports and fixes back to their place in the
module. An Angular app's config sets both ([frameworks.md](frameworks.md)). The rules never import
either; `@polymorph/rules` names both as optional peers, and `verify` loads them only for an
Angular fragment (`framework: 'angular'`) or a `.html` file. A module is Angular when the config's
settings say so (`angularSettings`) or when it imports from `@angular/`, `@polymorph/angular` or
`@polymorph/angular-ui`. The reports are the same sentences, with each answer computed from what was
written in template syntax: a member by its selector and a prop as a binding
(`<pm-inline [gap]="4">` where TSX says `<Inline gap={4}>`, `(click)="save()"` for `onClick={save}`,
`[iconOnly]="true"` for a bare `iconOnly`, because a bare attribute passes Angular's empty string).
A rule's fixed sentence is written once, as JSX, as it is for a Vue template.

| Rule | What it reads in a component | Example |
| --- | --- | --- |
| `no-raw-styles` | `class` and `style` in each spelling: static, bound whole (`[class]`, `[style]`, `[attr.class]`, `[ngClass]`, `[ngStyle]`) and one at a time (`[class.active]`, `[style.padding.px]`). A static one on a member is removed, because a member strips its host's attributes. A bound one on a member, and any on a part drawn as its own element (`<tr pmTableRow>`), is reported and left, because it can still reach the element. A class on a plain element and a style on anything that is not a member are reported with what they read as. A raw colour or length in a static attribute or a bound string | `<pm-button class="wide" label="Go" />` → `<pm-button label="Go" />` |
| `no-raw-interactive` | a raw `<button>`, `<input>`, `<select>`, `<textarea>`, `<option>` or `<optgroup>`; a listener (`(click)`, `(keydown.enter)`) on a plain element. A listener on `window` or `document` (`(window:keydown)`) is not the element's, and an `<a>` with a `routerLink` is a link. Options written by `@for` are not counted. Nothing is rewritten | ``Unexpected `(click)` on <div>. A clickable <div> has no control's states or keyboard path: use `<pm-button variant="ghost" label="…">` (rung 1), …`` |
| `no-app-css` | a component's `styles`, read for what their rules become; each file `styleUrl` and `styleUrls` name, as an import of it; a `<style>` element in a template | ``Unexpected component `styles`. Its rules are `<pm-inline [gap]="4">` (rung 1), so the styles can go.`` |
| `no-external-icons` | an inline `<svg>`; an import of `lucide-angular`, `@lucide/angular`, `@fortawesome/angular-fontawesome` or `angular-feather`, or of a set named for icons (`@ng-icons/…`, `@angular/material/icon`). The lucide glyphs read as roles, and a set's module, component and providers (`LucideAngularModule`) name no glyph | ``Unexpected icon import `lucide-angular`. `Trash2` is `<pm-icon name="delete" />` (rung 1). …`` |
| `no-external-motion` | an import of `@angular/animations` or `@angular/platform-browser/animations`; a component's `animations`; a trigger (`[@fade]`, `@fade`) and an enter or leave animation (`animate.enter`, `[animate.enter]`, `(animate.leave)`) on any element. An import and the metadata are read by the file's `style()` calls (a height opens a section, an opacity or a transform enters), an enter or leave animation is an entrance and exit, and a trigger is read by its name; one whose name says neither is a zone | ``Unexpected `[@expand]` on <div>. It is a section opening and closing: `<pm-collapsible>` and `<pm-accordion>` animate their own (rung 1). …`` |
| `no-external-dataviz` | an import of `ng2-charts`, `ngx-echarts`, `@swimlane/ngx-charts`, `ng-apexcharts`, `highcharts-angular`, `angular-highcharts`, `ag-charts-angular` or any `@unovis/*` package | ``Unexpected charting import `ng2-charts`. …`` |
| `scoped-token-owners` | a pattern-scoped token in a static attribute or a bound string of a template, and in a module's strings but its inline template | ``"--pm-shell-*" belongs to app-shell.module.css and 1 more, not this file (…).`` |
| `one-opener` | `<pm-page-header>` and `<pm-hero>` in one template | ``Unexpected <pm-page-header> beside <pm-hero>: …`` |

A template never sees its module's imports, so a tag is read as Angular's compiler matches it, by
the vocabulary's selectors: `<pm-button>` is the member `Button`, `<pm-tabs-content>` the part
`Tabs.Content`, and a list item, a table's section, row or cell, or a description list's term or
detail with a `pm…` attribute (`<tr pmTableRow>`) a part drawn as that element. Any other element
with a `pm…` attribute is plain, so `<button pmX>` is a raw button. A tag with a hyphen that is not a member's is another library's component. A
`<pm-bespoke>` lifts what `<Bespoke>` lifts in TSX, and a component whose `imports` list `Bespoke`
is exempt from the import bans, because that is how its template can match `<pm-bespoke>`. A
module's strings are read as in TSX except its inline `template`, which the template parser reads,
and its `styles`, which `no-app-css` reads whole. `packages/rules/src/rules/angular.test.ts` runs
each rule over a template and the fixtures through `verify`, `messages.test.ts` holds the Angular
reports to the same standard, and `packages/rules/fixtures/angular/` holds a violating, a lawful
and a zoned component.

## The Stylelint rules

Source in `packages/rules/src/stylelint/index.js`. Rule names are exported as `RULE_NAMES`.

| Rule | What it forbids | Half | Rungs that answer it |
| --- | --- | --- | --- |
| `polymorph/token-values-only` | a raw colour, length, radius, shadow, type or duration value in a recipe — anything but `var(--pm-*)` and the short allowlist (`0`, `1px`, `2px`, `100%`, `auto`, viewport units, `9999px`) | vocabulary | none |
| `polymorph/scoped-token-owners` | declaring or reading a pattern-scoped token in a stylesheet that does not own the pattern (the CSS twin of the ESLint rule of the same name) | vocabulary | none |
| `polymorph/no-motion-outside-vocabulary` | `transition*`, `animation*` or `@keyframes` in application CSS | application | 1, 4 |
| `polymorph/no-theme-selectors` | `[data-system]`, `[data-palette]` or `[data-theme]` in a recipe's selectors — a recipe never knows which house system or palette it is in | vocabulary | none |
| `polymorph/no-member-selectors` | `[data-member]` in a recipe's selectors — a component branching on its own name | vocabulary | none |
| `polymorph/no-ghost-tokens` | a `var(--pm-…)` or `style(--pm-…)` naming a custom property the theme does not emit and the file does not declare | vocabulary (in a consumer, all CSS) | none |
| `polymorph/no-token-declarations` | declaring a `--pm-*` custom property in application CSS. Reading one is lawful | application | 1, 2, 3 |
| `polymorph/no-app-theme-selectors` | `[data-system]`, `[data-palette]`, `[data-mode]`, `[data-density]`, `[data-tone]` or `[data-motion]` in application CSS's selectors: a branch on the theme | application | 1, 2 |
| `polymorph/no-app-member-selectors` | `[data-member]` in application CSS's selectors: a member restyled from outside | application | 1, 5 |
| `polymorph/no-root-font-size` | a `font-size`, or a `font` shorthand with a size, on `:root` or `html` in application CSS | application | 2 |

The application rules hold application CSS to the theme's decisions. `token-values-only`
reads only the properties that carry a design value, and a custom property is not one, so without
them a stylesheet could re-declare every token without writing a raw value the rules see. A product that re-declares `--pm-accent-bg` per
palette and mode, scopes rules to `[data-palette]`, removes a Button's hover through
`[data-member]` and sets `:root { font-size: 81.25% }` has made four theme decisions where no law
checks them. Each decision has an owner: the palette, the system, the system's per-member
exceptions, the system's type scale and density.

### What the rungs mean for each rule

The rung numbers come from `RULE_CLIMB` in `packages/rules/src/ladder.ts`, one table for every rule
in both plugins. `packages/rules/src/fixtures.test.ts` requires an entry for every rule, naming only
rungs the ladder has, in ascending order. The reasoning for each rule:

- **A style decision** (`no-raw-styles`) is almost always answered by rung 1, because the variant
  exists. Otherwise, a `patch` re-assigns a token on a layout primitive or `Card`, and a genuine
  one-off goes in a zone.
- **A stylesheet** (`no-app-css`) has no rung 3, because a patch is a token name, not a rule set.
  The answer is the vocabulary, or the same decision written inline inside a zone. A package's
  own stylesheet belongs to the component it styles, so the file that hosts that component in a
  `<ThirdParty>` boundary imports it. The report names the boundary only in a file that imports a
  binding from the package, because a boundary hosts nothing anywhere else.
- **A raw control** (`no-raw-interactive`) is answered by the vocabulary's control. A one-off
  composition goes in a zone.
- **Motion or a chart library** (`no-external-motion`, `no-motion-outside-vocabulary`,
  `no-external-dataviz`) is answered at rung 1 when a member already does what the code does: a
  fade-in is an overlay's entrance, a height animation is `Collapsible`'s, recharts' `BarChart` is
  `<BarChart>`. Otherwise it is not answered by rungs 1 to 3. Motion binds to component state
  ([motion.md](motion.md)), and a screen cannot express it at all. A chart that needs more than the
  chart members' `data`, `series` and axis props is drawing something the vocabulary does not draw.
  A library that draws the chart itself is hosted in a `<ThirdParty>` boundary that names it. A
  package that hands out only maths and drawing primitives (`d3-*`, `@visx/*`) is drawn by hand in
  a zone.
- **A glyph** (`no-external-icons`) is answered at rung 1 by `<Icon name="…">` with an existing
  role. When no role has the meaning, the answer is promotion: the report says the meaning becomes
  a new role in polymorph's icon set, which a consumer asks polymorph for. Here, adding a role is
  one entry in `design/icons.json` (its lucide glyph, SF Symbol and Material symbol) and one in
  `packages/react/src/icon/map.tsx`, from which `pnpm shells` and `pnpm native:contracts`
  regenerate the other frameworks' and platforms' tables. That makes it the cheapest promotion in
  the system. Rung 4 answers only an inline `<svg>` that is one-off art rather than an icon.
- **A theme decision in application CSS** (`no-token-declarations`, `no-app-theme-selectors`,
  `no-app-member-selectors`, `no-root-font-size`) belongs first to the document that owns it: a
  colour to the palette, a radius, a shadow, the type scale and a per-member exception to the
  system ([theming.md](theming.md)). Editing a theme document is not an exception, so it has no
  rung, and each report names it. The rungs answer a local need: a member's `tone`, `variant` or
  `size` (rung 1), `<DensityScope>` or `<ToneScope>` for a subtree (rung 2), and a `patch` for
  one instance's spacing or radius (rung 3). A restyled member that no prop answers needs a
  variant, which is a promotion (rung 5). Rung 4 answers none of them: a stylesheet is not
  inside a zone, and a token declared in a zone would still reach the members inside it.
- **Two openers** (`one-opener`) are answered only by rung 1. A zone suspends vocabulary rules but
  never accessibility, and two `<h1>`s are an accessibility fault. The only fix is to pick one
  opener.
- **The vocabulary's own rules** have no rung. Each is answered by fixing the code: the token
  (`token-values-only`), the pattern's owner or a theme-scoped token (`scoped-token-owners`), a
  token value or a style query on an exposed axis such as `@container style(--pm-axis-depth: flat)`
  (`no-theme-selectors`), a per-member exception in the system file
  ([below](#per-member-exceptions-in-a-system-file)) (`no-member-selectors`), the right spelling
  (`no-ghost-tokens`, whose message suggests the nearest real token), or an import through
  `@polymorph/react` or `@polymorph/engine` (`vendorable-imports`).

Violations carry their rungs. The MCP server's `validate` tool returns them with each diagnostic,
and the system card (`pnpm registry`) lists the rules and the ladder. See [tooling.md](tooling.md).

### What the rules say

**Every violation carries its answer.** A violation that leaves its reader to find the answer costs
an agent another attempt, and a person reads it as a refusal. So each message either comes with
the one lawful rewrite, as a fix (below), or names the lawful alternatives for what was written: the
member, the prop and the token to use instead, specific to the code, never a general sentence. Each
message is under 200 characters, and the sentence after the finding carries the answer.

The names are written so a program can read them back. Each answer is one code span: a member as
`` `<Inline gap={4}>` ``, a prop as `` `gap={4}` ``, a token as `` `--pm-space-4` ``. What was found is
written outside a span or in one no answer has the shape of. The MCP server's `validate` returns each
diagnostic with `fix` (the rule's edit, when it has one), `alternatives` (`{ member?, prop?, token?,
rung }`, read from the message by `packages/rules/src/rules/alternatives.ts`) and the message. For
an application rule a token named on its own is on rung 4, because application code writes a
`var(--pm-…)` only inside a zone; the prop or member beside it is the rung-1 answer.
`packages/rules/src/rules/messages.test.ts` holds every report to the standard.

A raw value is reported with the nearest token by value: a colour in OKLab with its alpha, among
the roles the property paints (`color` is a text role, `background` a background role, a border
colour a border role), and a length among the steps of its property's family (space, radius, type
size for `font-size` and the `font` shorthand, control height). Two steps equally near are both
named, and a negative length is named by its size and said to be negated. The rules receive the
values as the `values` option of `no-raw-styles`, `no-app-css` and `token-values-only`, because the
rules never import the engine. Without the option, the report names the token family instead of the
step.

Where the values come from depends on the repository. In this one, `eslint.config.ts` and
`stylelint.config.js` build them with `tokenValues(root)` from `@polymorph/rules/stylelint/emitted`,
which reads `design/` and resolves the reference pairing: the alphabetically first system in
`design/systems/` with its own default palette, in its default mode and density. `tokenValues` is
for this repository and the installer's tests, and a root without `design/systems/` is an error
that names the directory. A consumer never calls it: `polymorph add` writes the values into the
config fragments it generates ([below](#in-a-consumer)), read from the consumer's own compiled
theme.

### What the rules fix

Some violations have exactly one lawful rewrite, and for those the rule has a fix. `eslint --fix`
applies them, and so does an editor that fixes on save. An agent gets the same fixes through the MCP
tools `fix` and `fix_file` ([tooling.md](tooling.md)).

| Rule | What it rewrites | What it leaves reported |
| --- | --- | --- |
| `polymorph/no-raw-styles` | removes a `className`, `style` or `css` from a vocabulary component. No member takes one, so the attribute already does nothing | the same prop on a plain element, and every raw colour or length. There the style has an effect, and choosing its replacement is a design decision, so the report names the rewrite it reads as |
| `polymorph/no-external-icons` | an import from `lucide-react` becomes the gateway, where `design/icons.json` names the role each glyph draws: `<Trash2 />` → `<Icon name="delete" />`. An `aria-label` becomes `label`; an import nothing uses is removed | a glyph no role uses (that is a promotion); a glyph two roles share (`RotateCw` is both `refresh` and `rotate`); a glyph given a `size`, a `color`, a `className` or a handler; a glyph passed as a value; any other icon package; an inline `<svg>` |
| `polymorph/no-raw-interactive` | a `<button>` whose whole content is its text becomes `Button`: `<button type="button" onClick={save}>Save</button>` → `<Button label="Save" onClick={save} />`. `onClick`, `disabled`, `aria-label`, `aria-labelledby` and `aria-describedby` go across as written. An `<input type="checkbox">` and its label become `Checkbox`, whether the label wraps it (`<label><input type="checkbox" name="terms" /> Accept terms</label>` → `<Checkbox label="Accept terms" name="terms" />`) or follows it with `htmlFor` naming its `id`. `checked`, `defaultChecked`, `disabled`, `name`, `value` and `id` go across, and an `onChange` that takes no arguments becomes `onCheckedChange`. A `<textarea>` becomes `Textarea`. `value`, `placeholder`, `disabled`, `readOnly`, `maxLength`, `name`, `id`, `rows`, `autoFocus`, `onBlur` and `onFocus` go across, and an `onChange` that reads only `event.target.value` takes the value instead: `(e) => setNote(e.target.value)` → `(value) => setNote(value)`. Off unless a config switches them on (below) | a `<button>` with any other content or prop (a `className`, a `style`, an `id`); a checkbox with any other prop, label content that is not text, its text before the box, or a handler that reads its event; a textarea with children, any other prop (`defaultValue`, a `className`, a `style`), or a handler that uses the event for more than its value; every other raw control; a handler on a plain element |

Two principles decide which violations get a fix, and they keep the list short.

**Exactly one lawful rewrite.** A `style` on a `<div>` can be answered by a variant, a layout
primitive, a `patch` or a zone. A stylesheet import can be answered by the vocabulary or a zone. A
motion or chart library can be answered by a member, which may not exist. Choosing between
these is the design decision that the [exception ladder](#the-exception-ladder) makes visible, and a
fixer that chose would hide it. Those violations therefore stay as reports, which name the
alternatives and their rungs. No Stylelint rule has a fix, because a raw value could map to many
tokens. `token-values-only` names the nearest token by value but does not rewrite to it, because the
nearest value is not always the role meant: white is both a background and the text on an accent.
`no-ghost-tokens` names the nearest real token in its message but does not rewrite to it either. A
wrong token name is usually a guess, such as `--pm-accent-fg` for `--pm-accent-contrast`, and its
nearest neighbour is then a different token one letter away.

**Everything carried across, or nothing touched.** A fix that replaces an element never drops
anything that had an effect on it. A glyph given `size={20}` is not rewritten, because the gateway's
size is one of three token steps and picking the step is a choice. A `<button>` with a `className`
is not rewritten, because picking the variant it meant is a choice. A comment inside the element
also stops the fix. A fix removes only what has no effect once the element is the member: what the
rule reports, where that already had no effect; an `aria-hidden` on a glyph with no label, because
the gateway already hides an unlabelled glyph; and the `<label>` that wraps or follows a checkbox,
because its text becomes `Checkbox`'s `label` and the member draws the same row.

What follows from these two principles:

- **A handler is carried only where its meaning cannot change.** `Checkbox` calls
  `onCheckedChange` with the checked state and `Textarea` calls `onChange` with the value first, so
  a native handler that reads its event would get something else. A handler that takes no
  arguments goes across as written, and one that reads only `event.target.value` is rewritten to
  take the value. A `function` that reads `arguments` sees the member's arguments whatever its
  parameters say, so it stops the fix; an arrow has no `arguments` of its own. A handler that
  writes `event.target.value` (assigns, increments or destructures into it) stops the fix too,
  because a parameter cannot take the write. Any other handler, including one passed by name,
  stops the fix, and the report says why.
- **A converted `<button>` says `type="submit"` unless the original said `type="button"`.** A
  `<button>` with no `type` submits the form it is in, and `Button`'s default does not. One file
  cannot show whether a form encloses the button, because the form may be a member such as
  `FormPage` or a parent in another module. The fix therefore keeps the behaviour and writes it out.
  Where there is no form, `type="submit"` does nothing, and the author can see it and delete it.
- **The control fixes are switched on by a config, not by the rule groups.** They have to name the
  module that `Button`, `Checkbox` and `Textarea` are imported from, and the groups are also used by
  repositories that vendor their members and import them by path. `fixableRawControls`, spread
  after the groups, sets `no-raw-interactive`'s `vocabulary` option to `@polymorph/react-ui`.
  This repository's `eslint.config.ts` does that for `apps/`. `fixableSolidControls` sets it to
  `@polymorph/solid-ui` for a Solid app. The gateway fix needs no option. `Icon` ships in
  `@polymorph/react`, which both kinds of consumer have, and the fix adds it to an existing import
  of `@polymorph/react-ui` where the file has one.
- **A fix checks what a name refers to.** A fix does not write `<Icon>` or `<Button>` where that
  name is a parameter or a local variable. It does not remove a `className` from a parameter that
  happens to be called `Card`.
- **A new import goes after the file's last import**, or below a `'use client'` directive in a file
  with no imports. Two kinds of file are left alone because no line is safe for the import. The
  first has no imports and no directive and opens with a comment, and whether the import belongs
  before or after that comment depends on what the comment says. The second has code on the same
  line as its last import.
- **Several passes.** Two fixes whose edits touch each other, such as two dead props side by side or
  two buttons that both need the `Button` import, are applied in separate passes. `--fix` and the
  MCP tools run all the passes. An integration that runs one pass gets only the first fix.
- **Fixes and reports that name a member are checked against the member's spec.**
  `packages/rules/src/rules/fix-api.test.ts` compares the props that the `<button>`, checkbox,
  textarea and glyph fixes write with `design/components/`, and every member and prop a report
  names (`SearchInput`, `<Table.Row interactive>`, `<DonutChart segments>`) with the same specs. A
  renamed member or prop therefore fails the suite instead of being written into other people's
  files or recommended to them.

### Halves of one law

A lint rule sees one file at a time. Three of the red rules have a matching law that reads the whole
repository at once, so it catches more:

| Red rule (travels to consumers) | Law (runs only here) | What only the law can see |
| --- | --- | --- |
| `no-app-css` | `packages/rules/src/repo-laws.test.ts` — "apps/ contains no stylesheets" | a stylesheet nobody imports, which ESLint never visits |
| `one-opener` | `repo-laws.test.ts` — "the one-h1 law counts a pair" | a page assembled across modules, with the `<Hero>` in one and the `<PageHeader>` in another |
| `no-ghost-tokens` | `packages/rules/src/token-references.test.ts` | a token declared in one stylesheet and read from another, which resolves at runtime through inheritance |

Consumers get the rule. The law runs only in this repository and is the more complete check. Where
the rule reports a false positive that the law would not, the correct response is a
`stylelint-disable-next-line` on that line. The known case is a token declared in one stylesheet and
read from another.

## Wiring the rules into a config

### The exported groups

The red rules are their own package, `@polymorph/rules`, a dev dependency of a consumer. Its
`@polymorph/rules/eslint` entry exports the ESLint plugin under these names:

| Export | Contents | Apply it to |
| --- | --- | --- |
| `stageOneRules` | `no-raw-styles`, `no-app-css` | application code: the rules about expressing style |
| `stageTwoRules` | `no-raw-interactive`, `no-external-motion`, `no-external-icons`, `no-external-dataviz`, `scoped-token-owners` (with the owner map), `one-opener` | application code: the rules about rebuilding or reaching past the vocabulary |
| `allRules` | both groups above | application code; this is what `polymorph add` applies |
| `fixableRawControls` | `no-raw-interactive` with `vocabulary: '@polymorph/react-ui'`, which switches its `<button>`, checkbox and textarea fixes on | spread after the groups, where application code imports members from `@polymorph/react-ui` |
| `solidSettings`, `fixableSolidControls` | the settings that read every TSX file as Solid, and `no-raw-interactive` with `vocabulary: '@polymorph/solid-ui'` | a Solid app: `settings: solidSettings` on the application block, and `fixableSolidControls` spread after the groups |
| `angularSettings` | the settings that read every TypeScript module as an Angular component, whose reports answer in template syntax | an Angular app: `settings: angularSettings` on the block for its modules and the block for its templates |
| `vendorableRules` | `vendorable-imports`, rooted at `packages/react-ui/src` | vendored component source; re-root `root` at your vendored directory |
| `plugin` (also the default export), `rules`, `PLUGIN_NAME` | the plugin object, its rule modules, and its name (`polymorph`) | register the plugin |
| `parser` | `@typescript-eslint/parser` | every rule reads TSX, which ESLint's default parser cannot |
| `SCOPED_TOKEN_OWNERS` | the owner map from `packages/rules/scoped-token-owners.json` | pass to `scoped-token-owners` if you configure it yourself |

`RULE_CLIMB` is exported from `@polymorph/rules` (and `@polymorph/rules/ladder`) for tooling, and
so are the modules each framework imports members from: `VOCABULARY_MODULE`,
`VUE_VOCABULARY_MODULE`, `SVELTE_VOCABULARY_MODULE`, `SOLID_VOCABULARY_MODULE` and
`ANGULAR_VOCABULARY_MODULE`.

`@polymorph/rules/stylelint` exports the Stylelint plugins as its default export (an array to
spread into `plugins`), `RULE_NAMES`, and `applicationRules`, the application half switched on, to
spread into the rules for your application's stylesheets. `no-ghost-tokens` must be given the
list of custom properties your theme emits: `[true, { tokens: [...] }]`. Without the list, it
reports an error on every stylesheet instead of passing them.

The rules are a separate package that only lint configs import. A bundler that follows a runtime
entry (`@polymorph/engine`, `@polymorph/react`, `@polymorph/react-ui`) therefore never reaches a
linter.

### In this repository

`eslint.config.ts` and `stylelint.config.js` at the root are the reference configuration:

| Config block | Files | Rules |
| --- | --- | --- |
| `polymorph/red-rules-stage-1` | `apps/**/*.{ts,tsx}`, minus `apps/*/src/harness/**` | `stageOneRules` |
| `polymorph/red-rules-stage-2` | the same | `stageTwoRules`, then `fixableRawControls` |
| `polymorph/vocabulary-containment` | `packages/{react-ui,react,engine}/**/*.{ts,tsx}` | `no-external-icons`, `no-external-motion`, `no-external-dataviz`, each with its gateway in `allowIn` |

| Stylelint override | `apps/**/*.css` | `applicationRules`: `no-motion-outside-vocabulary`, `no-token-declarations`, `no-app-theme-selectors`, `no-app-member-selectors`, `no-root-font-size` |

A rule that is listed in a config is not necessarily applied to anything. `repo-laws.test.ts` asks
ESLint and Stylelint which rules actually govern a sample file in each tree, so a rule that stops
being applied fails the suite.

### In a consumer

`polymorph add` writes two generated fragments next to your configs and links them in. Both load
the rules from `@polymorph/rules`, which you install as a dev dependency
([consuming.md](consuming.md#2-dependencies)):

```js
// eslint.config.js — `polymorph add` inserts the import and the spread
import polymorph from './polymorph.eslint.js'

export default [...polymorph /* , your own config objects */]
```

```js
// stylelint.config.js — `polymorph add` adds the fragment to `extends`
export default { extends: ['./polymorph.stylelint.js'] }
```

`polymorph.eslint.js` sets the TSX parser, applies `allRules` to every `.ts`/`.tsx` file outside the
vendored directory, and applies `vendorable-imports` rooted at the vendored directory. In a Vue app
(`--framework vue`) it also parses `.vue` files with `vue-eslint-parser`, which the app installs as
a dev dependency, and applies the same rules to them. A Svelte app's fragment does the same for
`.svelte` files with `svelte-eslint-parser`. A Solid app's fragment sets `solidSettings` on the
application block, so every TSX file reads as Solid. An Angular app's fragment sets
`angularSettings` and the inline-template processor on its `.ts` files, and parses `.html` files,
external templates and the inline ones the processor extracts, with
`@angular-eslint/template-parser`; the app installs both `@angular-eslint` packages as dev
dependencies.
`polymorph.stylelint.js` applies the application half (`no-motion-outside-vocabulary`,
`no-token-declarations`, `no-app-theme-selectors`, `no-app-member-selectors`, `no-root-font-size`)
and `no-ghost-tokens` to every stylesheet, then lifts the application half and adds
`token-values-only` for the vendored directory, where the recipes declare transitions and the
compiled theme declares every token under pairing selectors.
Every `polymorph add` and `polymorph update` rewrites both files, and also refreshes the token list
that `no-ghost-tokens` checks against. If a token you know exists is reported as a ghost, the list
is older than your vocabulary. Run `polymorph update`.

To use the rules without vendoring, import the groups directly.
[consuming.md](consuming.md#6-the-red-rules) has the config.

A repository with no lint config at all can still run the rules: `polymorph check <dir>` runs
`verify` over every file the rules read below a directory, as application code, and exits 1 on
any violation ([tooling.md](tooling.md)). It reports what the configs above would report.

## The exception ladder

Real products need one-offs: a campaign page, a bespoke illustration, one unusual screen.
**Exceptions are not forbidden; undeclared exceptions are.** Drift is deviation that nobody can see.
A declared, bounded exception that appears in the inventory is a design decision, with an owner, a
location and a visible cost.

The ladder runs from most governed to least. Always use the highest rung that works.

### The rungs of the exception ladder

1. **Variant selection** — Pick a variant, size or tone the member already offers. This is the vocabulary's built-in range, and it covers most needs.
2. **Contextual re-assignment** — A subtree re-assigns a named decision such as density or tone. It is declared with `<DensityScope>` or `<ToneScope>`. Every value still comes from the theme, and every law still checks it.
3. **Instance patch** — One instance re-assigns semantic tokens, never raw values. It is declared with the `patch` prop on `Stack`, `Inline`, `Grid` or `Card`. Its values are typed token steps, and the inventory lists it.
4. **Bespoke zone** — A declared boundary for genuinely one-off composition, or around another library's component. Inside `<Bespoke reason="…">` the vocabulary rules are suspended. `<ThirdParty library="…" reason="…">` hosts a component another library draws, and lifts only what hosting it needs. Either still reads theme tokens for anything it shares with the system, accessibility is never suspended, and its styling applies only to the elements it renders.
5. **Promotion** — A recurring patch or zone is promoted into the vocabulary or deleted. This is how an exception leaves the ladder. A one-off may occur only once, and the inventory shows when one recurs.

### Rung 1: variant selection

Every member exposes its range as typed props (`variant`, `tone`, `size`, spacing steps). The prop
types are enums, so a value off the scale is a type error, not a review comment. Before trying
anything else, read the member's spec in `design/components/<member>.md` or its entry in the system
card.

### Rung 2: contextual scopes

`DensityScope` and `ToneScope` (`packages/react-ui/src/exceptions/Scopes.tsx`) set the same
attribute that the theme runtime sets on `<html>`, but on a subtree. They add no new values. Every
token still comes from the theme, and only the choice of which variant applies changes. The theme
has already emitted every variant.

```tsx
import { DensityScope, ToneScope } from '@polymorph/react-ui'

<DensityScope value="compact" as="section">   {/* compact | standard | comfortable */}
  <DataTable … />
</DensityScope>

<ToneScope value="inverse">                   {/* re-declares surface, text and border roles from the opposite mode */}
  …
</ToneScope>
```

- `DensityScope` changes space and component dimensions only, never the type scale.
- `ToneScope` has one value, `inverse`. An inversion uses the opposite mode. It is not a second
  palette.
- `as` is `div` (the default), `section` or `span`. A scope is a wrapper, not a surface.

A nested theme scope, where a subtree uses an entirely different pairing, is a theming feature, not
an exception. See [theming.md](theming.md).

### Rung 3: instance patches

A `patch` re-assigns token steps on one instance. Its keys are the spacing props the component
already exposes, and its values are **token names, never lengths**:

```tsx
<Stack gap={6} patch={{ gap: 2 }}>…</Stack>   {/* LayoutPatch: gap, p, px, py */}
<Card patch={{ p: 4, radius: 'sm' }}>…</Card>  {/* CardPatch: p, px, py, radius */}
```

`Stack`, `Inline` and `Grid` take `LayoutPatch` (`packages/engine/src/conventions/spacing.ts`).
`Card` takes `CardPatch` (`packages/react-ui/src/structure/Card.tsx`). On the layout primitives a
patch is applied after the base props, and `patch={{ gap: undefined }}` cannot erase the base value.

### Rung 4: Bespoke zones

`Bespoke` (`packages/react-ui/src/exceptions/Bespoke.tsx`) declares the exception. Its `reason` prop
is required, because the inventory prints it and reviewers read it.

```tsx
import { Bespoke } from '@polymorph/react-ui'

<Bespoke reason="Promo illustration: overlapping discs the vocabulary has no shape primitive for.">
  <div style={{ padding: 'var(--pm-space-4)', background: 'var(--pm-accent-subtle)' }}>…</div>
</Bespoke>
```

The zone renders a `<div data-bespoke={reason}>` with `display: contents`. It draws nothing and
inherits everything, so `--pm-*` tokens cascade into it and bespoke work re-themes with the rest of
the product. `apps/workbench/src/relay/WhatsNew.tsx` is a complete example.

The exemption is implemented in the rules themselves (`packages/rules/src/rules/jsx.ts`), never in a
disable comment. The rules look for a real `<Bespoke>` element: a JSX element in TSX, and the
element in Vue, Svelte or Angular markup (`<pm-bespoke>` in Angular). The text `<Bespoke` in a
comment or a string does not count. What a zone lifts:

| Rule | Lifted inside the zone |
| --- | --- |
| `no-raw-styles` | `style` and `css` props, a `className` on a plain element, and raw values, inside the element. A `className` on a vocabulary component stays red. |
| `no-raw-interactive` | raw controls and handled elements inside the element |
| `no-external-icons` | inline `<svg>` inside the element; icon-set imports anywhere in a file that declares a zone |
| `no-external-motion`, `no-external-dataviz` | imports anywhere in a file that declares a zone, because an import cannot be scoped to an element |
| `no-app-css`, `scoped-token-owners`, `one-opener`, the Stylelint rules | **nothing** |

A zone therefore styles itself with `style` props. A stylesheet import from application code fails
with or without a zone.

What a zone does not turn off:

- **The theme.** Use `var(--pm-*)` for anything the zone shares with the system (colour, type,
  space) so that it re-themes. Inside a zone the rules do not check values, so the reviewer
  checks this, and the inventory is how the reviewer finds the zone.
- **Accessibility.** It is never suspended, anywhere. `one-opener` deliberately applies inside zones
  too. Decorative art inside a zone is `aria-hidden`, and a meaningful image still has a label.
- **Containment.** A zone styles the elements it renders and nothing else. The vocabulary members it
  composes keep their own appearance. A zone around a `<Button>` does not permit a `className` on
  it.

### Rung 4: another library's component

Some components are not worth drawing twice: a map, a rich-text editor, a data grid, a
drag-and-drop board. `ThirdParty` (`packages/react-ui/src/exceptions/ThirdParty.tsx`) declares the
boundary around one. `library` names the package as it is imported, and `reason` says why the
vocabulary was not enough. Both are required, because the inventory prints both.

```tsx
import { latLng } from 'leaflet'
import 'leaflet/dist/leaflet.css'
import { MapContainer, TileLayer } from 'react-leaflet'

import { useThemeValues } from '@polymorph/react'
import { ThirdParty } from '@polymorph/react-ui'

const CENTRE = latLng(51.5, -0.1)

export function Depots() {
  const theme = useThemeValues()
  return (
    <ThirdParty library="leaflet" reason="Depot map: no member draws map tiles.">
      <div style={{ height: '320px', borderRadius: 'var(--pm-radius-surface)' }}>
        <MapContainer
          style={{ height: '100%', background: theme.color('bg.subtle') }}
          center={CENTRE}
          zoom={11}
        >
          <TileLayer url="…" />
        </MapContainer>
      </div>
    </ThirdParty>
  )
}
```

The boundary renders a `<div data-third-party={library} data-reason={reason}>` with
`display: contents`. It draws nothing and inherits everything, as a zone does.

**A boundary hosts the library only in a file that imports it.** A boundary lifts nothing unless
the file imports a binding from the library it names: a default, a name or a namespace, from that
specifier or from a path inside it (`chart.js/auto` under `chart.js`), an `import()` of one, or
TypeScript's `import L = require('leaflet')`. The import is what ties the name to code. Without it a boundary could name any package, or one that
does not exist, and lift the bans for whatever it wraps, and the inventory would list a library
the file does not use.

Some imports bring no binding in. An import for its side effect (`import 'leaflet'`) names
nothing the file can use. A type import is gone before the code runs. A re-export hands the module
on without using it. A stylesheet import is not the library, with a default or without
(`import sheet from 'leaflet/dist/leaflet.css?inline'`), because what it exports is the
stylesheet's text or its class names. So a package that is only a stylesheet (`normalize.css`) is
never hosted, and neither is a package the file takes only the stylesheet of
(`bootstrap/dist/css/bootstrap.css`). The stylesheet stays red in both cases, and its report
offers no boundary.

A wrapper is a package of its own. `react-leaflet` brings no binding from `leaflet`, so the file
above imports `latLng` from `leaflet` to host it and to have its stylesheet lifted. A file that
names `react-leaflet` hosts the wrapper, and `leaflet/dist/leaflet.css` stays red there.

`no-raw-styles` reports a boundary that hosts nothing, on its own tag, and what the boundary holds
is read as if the boundary were not there. These boundaries host nothing:

- one with no `library`, or an empty one;
- one with a computed `library` (`library={name}`, `:library="name"`, `[library]="name"`), because
  no rule can compare a computed name with the file's imports;
- one whose `library` is not spelled as an npm package (`./maps`, `@/maps`);
- one whose `library` is a polymorph package or a framework's own runtime;
- one whose package the file imports no binding from.

**A boundary cannot name polymorph or the framework.** A file imports these whether it hosts
anything or not: the import of `ThirdParty` is itself a binding from the vocabulary, and a
component is written with its framework. A boundary that named one would host in every file, and
that is a zone for `style`, a class and a length with a library's name on it. None of them is
another library's component either. So a `library` that is one of these packages, or a path
inside one (`react-dom/client`, `svelte/store`), hosts nothing:

- a polymorph package: any `@polymorph/*`;
- React's runtime: `react` and `react-dom`;
- Vue's: `vue`, and the packages it is built from (`@vue/runtime-core`, `@vue/runtime-dom`,
  `@vue/reactivity`, `@vue/shared`, `@vue/server-renderer`);
- Svelte's: `svelte`;
- Solid's: `solid-js`;
- Angular's: the packages of the framework's own repository (`@angular/core`, `@angular/common`,
  `@angular/compiler`, `@angular/forms`, `@angular/router`, `@angular/animations`,
  `@angular/platform-browser`, `@angular/platform-browser-dynamic`, `@angular/platform-server`,
  `@angular/elements`, `@angular/service-worker`, `@angular/localize`, `@angular/upgrade`).

A component library published in a framework's scope is still a library: `@angular/cdk`,
`@angular/material` and `@angular/google-maps` host. So does a router or a meta-framework
published apart from its framework (`vue-router`, `next`), because a file imports one for what it
uses and the inventory lists it. The list is `FRAMEWORK_RUNTIMES` in
`packages/rules/src/rules/jsx.ts`.

**Which specifiers are the application's own.** A specifier is read as a package when it is
spelled as an npm package name: an optional `@scope/`, a name, and any path after it (`leaflet`,
`@tiptap/core`, `leaflet/dist/leaflet.css`). Every other specifier is the application's own, and
nothing lifts a stylesheet imported through one: a relative or an absolute path (`./depots.css`,
`/src/app.css`), a `#` import (`#styles/row.css`), and an alias no package name can spell
(`@/styles/app.css`, `~/app.css`, `$lib/app.css`). An alias spelled as a package name
(`styles/app.css`, `@app/styles/theme.css`) cannot be told from a package by its spelling, and the
rules do not read a bundler's or TypeScript's alias table. The binding rule covers the common
case: a file that only imports the stylesheet hosts nothing. A file that also imports a binding
through the alias and names the alias in a boundary is read as hosting a library of that name, and
the inventory lists the alias among the hosted libraries, where a review sees it.

**A boundary with no children** is read as one with children. It declares its library for the
file, so the library's import and stylesheet are lifted when the file imports a binding from the
library, and it lifts nothing else because it holds nothing. A library that draws outside the
tree, such as a tour or a lightbox mounted on `document.body`, is declared this way. No rule
treats a childless boundary differently, because the import is what ties a boundary to its
library, and no rule can tell what a boundary's children are.

It is a separate boundary from `Bespoke` because it lifts less. A zone suspends the vocabulary
rules for composition the application writes itself. A boundary that hosts its library lifts what
hosting that library needs, and the rest of the rules still read the file:

| Rule | Inside a `<ThirdParty>` that hosts its library |
| --- | --- |
| `no-raw-styles` | **Lifted:** `style` and a class on a plain element and on the library's own component, and a raw length, inside the element. **Kept:** a colour, in any syntax in the `style` and as `#hex` or a colour function anywhere else in the file, a `style` whose property names are not written out (`style={styles}`), and a `className` or `style` on a vocabulary component or on a part of one (`<Table.Row>`, `<List.Item>`). |
| `no-app-css` | **Lifted:** a stylesheet imported from the package of the library the boundary names, anywhere in the file that declares it. **Kept:** every other stylesheet: the application's own, another package's, and the stylesheet of a package the file imports no binding from. |
| `no-external-motion`, `no-external-dataviz` | **Lifted:** an import of the library the boundary names, anywhere in the file that declares it. **Kept:** every other banned library, another package of the same npm scope included, and a re-export of any. |
| `no-raw-interactive` | **Kept.** A control beside the hosted component is a member: a `<Button>` that calls the library's API. |
| `no-external-icons` | **Kept.** A glyph is `<Icon name="…">`. |
| `scoped-token-owners`, `one-opener`, the Stylelint rules | **Kept.** |

The library a boundary names is one package: the package itself and any path inside it
(`leaflet/dist/leaflet.css`, `chart.js/auto`). Another package of the same npm scope is another
library, because a scope is a publisher's namespace and not one library published in parts.
`@angular/google-maps` does not host `@angular/material`, and `@swimlane/ngx-datatable` does not
host `@swimlane/ngx-charts`. An import a rule bans is lifted only for a boundary that names the
banned entry as the rule lists it. A framework's own motion modules (`svelte/transition`,
`@angular/animations`) are on the motion rule's list and inside a runtime no boundary can name, so
no boundary lifts them: motion the application writes itself goes in a zone. A file that needs
two packages lifted (`chart.js` and `react-chartjs-2`) declares a boundary for each, one inside
the other, and the inventory lists both. A package that is on no banned list and ships no
stylesheet needs nothing lifted: the Tiptap editor names `@tiptap/core` and imports
`@tiptap/starter-kit` beside it.

A part of a member keeps the member's ban inside the boundary. The boundary lifts a `style` and a
class on what the library draws, and `<Table.Row>` is drawn by the vocabulary, so its `style` and
its class are removed there as a member's are. A dotted name whose root is not an imported member
(`<Leaflet.MapContainer>`) is the library's own and takes both. Outside a boundary a part is not
read as a member: its `style` is reported, and its class is left alone.

A disable comment inside a `<ThirdParty>` is still undeclared. Only a `<Bespoke>` accounts for a
disable, because a disable inside a boundary would widen it without saying so. Hosted code that
needs a raw control or an inline `<svg>` of its own goes in a zone.

**The theme reaches a hosted component two ways.**

- _Through CSS._ The boundary inherits every `--pm-*` custom property, so a library that is styled
  with CSS, or exposes custom properties of its own, reads the theme in a `style` on the element
  that holds it: `style={{ '--rdg-background-color': 'var(--pm-bg-surface)' } as CSSProperties}`.
  React's `CSSProperties` type names no custom property, so TSX writes the object with a cast,
  which the rule reads through. A value written this way follows the pairing, the mode and the
  density with no code.
- _As data._ A library that takes colours, radii, type and spacing through a JavaScript API cannot
  read a custom property. `useThemeValues()` returns the theme's resolved values where the hook
  is used, and returns new ones when the pairing, the mode, the density, the contrast preference
  or the reading direction changes: `theme.color('accent.bg')` is `#5b4bd6`, `theme.space(4)` is
  `16`, `theme.radius('control')` is `8`, `theme.text('sm')` is a family, a size and a line height
  in pixels, and `theme.direction` is `'ltr'` or `'rtl'`. [theming.md](theming.md) lists what it
  returns. Read a value where the framework runs again on a change: while a React component
  renders, in a Vue, Svelte or Angular template, in Solid's JSX, or in an effect or a computed
  value in any of them. A server has no document to read, so a server render gets empty values
  (`theme.themed` is false and a colour is the empty string), and the page gets the document's
  values once it has hydrated ([frameworks.md](frameworks.md#another-librarys-component)).

A colour is the one value the boundary does not let a file write, because a hosted component
that keeps its own colours is the first thing that breaks when the pairing or the mode changes.
The report on a raw colour in a file that hosts a library names the nearest role and
`useThemeValues()`.

A colour is refused in every syntax, and the rule reads it two ways. A colour in a syntax the
rule's patterns name (`#hex`, `rgb()`, `hsl()`, `oklch()` and the other colour functions of that
kind) is reported wherever the file writes it, as it is in any application file. Every other
syntax is refused in the `style` the boundary lifts, by what the declaration's property may
take:

- A property that takes a colour (`color`, `fill`, `stroke`, any `*-color`, a custom property
  whose name ends in `color` such as `--rdg-background-color`) takes a custom property read
  (`var(--pm-bg-subtle)`), a keyword that names no colour (`transparent`, `currentColor`,
  `inherit`, `none`), or a value computed where it is written, such as `theme.color('bg.subtle')`.
- A shorthand that carries a colour (`border`, `background`, `border-image`, `outline`,
  `column-rule`, `box-shadow`, `text-shadow`, `text-decoration`, `text-emphasis`, `filter`,
  `caret`) also takes the other words and functions of its grammar: `1px solid`,
  `url(…) no-repeat center / cover`, `linear-gradient(to right, …)`, `1 fill stretch`.
- Any other word or function in such a property is refused: a named colour (`red`), a system
  colour (`ButtonText`), a fallback (`var(--pm-text-primary, black)`).
- `color-mix()`, `color()`, `light-dark()`, `contrast-color()` and `device-cmyk()` are refused in
  every property, a custom property included.

The check lists what a colour property may take and not the colours, because a list of colour
names and functions is out of date when CSS adds one, and a missing entry would pass without a
report. With what is allowed listed, a syntax the rule has never seen is refused. The words a
shorthand takes are a fixed part of its grammar, so that list is short and does not grow with the
colour syntaxes (`refusedColour` in `packages/rules/src/rules/raw-values.ts`). Each grammar is
listed whole, because a keyword the list lacks is reported as a colour, and a report on a lawful
value inside a boundary has no answer but a zone. `raw-values.test.ts` holds a lawful value for
every word on the list, and checks that no word on it is a named colour or a system colour.

The check reads the `style` through every form whose property names are written out: a type
assertion (`as CSSProperties`, `satisfies`, `!`), each end of a conditional and of `||` and `??`,
the right of `&&`, an object spread into the object, Vue's array of styles (`:style="[…]"`), an
object under a selector in a `css` prop, and CSS text with values computed inside it
(`` `height: ${h}px` ``, `style="height: {h}px"`, `style="height: {{h}}px"`). A value computed
inside CSS text is read as `0`, so the words beside it are still read. The reader is
`packages/rules/src/rules/lifted-style.ts`.

**A `style` the rule cannot read is refused inside a boundary.** `no-raw-styles` reports a `style`
whose property names are not written out: one given as a variable (`style={styles}`), a call or a
member (`theme.styles`), a spread of anything but an object written out, a computed key that is
not a string, CSS text with a computed name or computed declarations (`` `${base}; height: 4px` ``),
Svelte's shorthand `{style}`, and a bound Vue or Angular `style` that is not an object, an array
or a string written out (`[ngStyle]="styles"`). The boundary lifts a `style` and keeps a colour
red, and it can keep a colour red only in a `style` the rule can read, so the answer is to write
the object or the text in place. A value given through a variable has its name written out
(`style={{ height }}`, `style={{ color: tone }}`): it is lawful, and the colour it holds is not
checked.

The check does not read a custom property that is not named for colour (`--grid-accent: white`),
a value that reaches the `style` through a variable, a `style` passed in a spread of attributes
(`{...props}`, `v-bind="props"`), or a prop of the library's own component
(`<Polyline color="red">`), because a library's props are its own. A custom property with `color`
inside its name (`--grid-color-mode: dark`) is not named for colour:
it may hold a mode or a scheme, whose words no list can hold. A mask (`mask`, `mask-image`) is not
read either, because a mask paints no colour: only its alpha or its luminance is used.

**React, Vue, Svelte, Solid and Angular have the boundary and the hook.** Each vocabulary ships
`ThirdParty` under the same name (`<pm-third-party>` in an Angular template), and each foundation
ships `useThemeValues` in the shape its framework reads a value ([frameworks.md](frameworks.md)).
The elements have the boundary as `<poly-third-party>` and the engine's `readThemeValues` in place
of the hook, and no rule reads an elements page. The
rules read the boundary in TSX, a Vue template, Svelte markup and an Angular template. An Angular
component's imports are in its module and its boundary is in its template, so the rules read the
template the component names, inline or by `templateUrl`. The template is linted as a program of
its own, which sees no import. So the module reports a boundary whose package it imports no
binding from, on the tag in an inline template or on `templateUrl`. In the template's own pass
that boundary still lifts a `style` and a class on what it holds. The component is red either way.

On iOS and Android the member is absent. Its rules are lint rules for web code, and a native
screen that hosts another library's view declares a `Bespoke` zone.

**What no rule does.** The rules are syntactic, so none can tell another library's component from
the application's own, and none reports a hosted component that has no boundary. None checks that
what a boundary holds is drawn by the library it names: the import ties the name to the file, not
to the children. What makes the
declaration necessary is what the boundary lifts: the library's stylesheet, a `style` on its
component, and the import of a chart or motion library. A library that draws nothing and needs
none of those, such as a date library or a headless table, needs no boundary. `pnpm inventory`
lists the declared ones.

`apps/workbench/src/hosted/` holds two complete examples, which the workbench shows at `/hosted`.
`DepotMap.tsx` hosts a Leaflet map and takes the theme as data, and `NoteEditor.tsx` hosts a
Tiptap editor and takes it through CSS. `hosted.test.tsx` shows each one following the pairing
and the mode in a real browser. `packages/rules/src/rules/third-party.test.ts` states what the
boundary lifts and keeps in each of the five syntaxes: the binding a boundary needs to host, the
class and the `style` a member and its parts still refuse, and the colours a lifted `style` may
not write. Each framework's fixtures hold a hosted screen (`app-third-party.*`).

### Rung 5: promotion

When the inventory shows the same patch or zone recurring, the vocabulary is missing something. Add
it (a variant, a prop, a token, an icon role or a new member) by amending the member's spec in
`design/components/` and implementing it. Then delete the exceptions it replaces.
[CONTRIBUTING.md](../CONTRIBUTING.md) describes how to add a new member. A recurring exception is
either promoted or deleted. A genuine one-off stays a declared one-off.

`Select`'s `emptyOption` prop is an example of a promotion. An "any" choice belongs to the member,
not to a sentinel value that each screen invents. A gap that is still open is recorded where it
occurs instead of being worked around. `apps/workbench/src/relay/NewTicketPage.tsx` records that
`Combobox` cannot match an option on text it does not display.

### Installing the ladder in a consumer

The ladder's primitives are vendorable like any member:

```sh
polymorph add bespoke third-party density-scope tone-scope
```

With `--framework`, the same command vendors the Vue, Svelte, Solid or Angular primitives. Each
framework's vocabulary ships them under the same names, and an Angular template writes them as
`<pm-bespoke>`, `<pm-third-party>`, `<pm-density-scope>` and `<pm-tone-scope>`.

The red rules recognise a vendored `<Bespoke>` or `<ThirdParty>` by its element name, so a zone or
a boundary in a consumer counts as declared, just as it does here.

### Per-member exceptions in a system file

A house system can also declare a deviation for one member, in its own JSON file instead of in a
recipe. `overrides.exceptions` in `design/systems/<name>.json` points one class token (radius,
shadow or inset) for one named member at one lawful step, with a required `because`. The theme
emitter writes it as a `[data-member="…"]` block. This is the only lawful use of that attribute,
which is why `no-member-selectors` forbids it in recipes. See [theming.md](theming.md).

## The inventory

```sh
pnpm inventory
```

The command runs `packages/rules/bin/inventory.js`, which scans with
`packages/rules/src/inventory.js`. It reads every `apps/**/*.{ts,tsx,vue,svelte,html}` file outside
`apps/*/src/harness/**`, `node_modules` and `dist`, and reports every deviation from the vocabulary.
A Vue or Svelte component's scripts are read as TypeScript, and its markup for the same elements, a
`patch` attribute in any of Vue's or Svelte's spellings (`patch="…"`, `:patch="…"`, `patch={…}`),
and disables written in HTML comments. An Angular component's inline templates and its external
`.html` templates are read the same way, each member by its selector (`<pm-bespoke>`,
`<pm-third-party>`, `<pm-density-scope>`) and a `patch` static or bound (`[patch]="…"`).

A template's tags and attributes are read as lint reads them (`packages/rules/src/markup.js`), so
a zone or a boundary lint honours is one the inventory lists. A Vue tag is read by the name Vue
resolves it to: `<third-party>` is `<ThirdParty>`, and `<bespoke>` is `<Bespoke>` in a file whose
script imports `Bespoke`. A boundary's library is what its `library` attribute writes out. A
`data-library`, a bound `library` and the word inside a `reason` name none.

| Rung | What it finds | What it reports as the reason |
| --- | --- | --- |
| 2 | each `<DensityScope>` and `<ToneScope>` | its `value` |
| 3 | each element with a `patch` prop | the patch |
| 4 | each `<Bespoke>` | its `reason` |
| 4 | each `<ThirdParty>`, with the library it names | its `reason` |
| none | an `eslint-disable`, `eslint-disable-next-line` or `eslint-disable-line` comment naming a `polymorph/` rule outside every `<Bespoke>` element | the rules it disables |
| none | a `<ThirdParty>` that writes no `library` out, as `ThirdParty with no library` | its `reason` |

```
RUNG    WHERE                                         WHAT                     WHY
------  --------------------------------------------  -----------------------  ----------------------------------------------------------
rung 4  apps/workbench/src/hosted/DepotMap.tsx:138    ThirdParty leaflet       Depot map: no member pans and zooms over places.
rung 4  apps/workbench/src/hosted/NoteEditor.tsx:114  ThirdParty @tiptap/core  Shift note: no member edits formatted text.
rung 2  apps/workbench/src/relay/InboxPage.tsx:271    DensityScope             compact
rung 4  apps/workbench/src/relay/WhatsNew.tsx:26      Bespoke                  Promo illustration: overlapping discs the vocabulary has …

4 declared exception(s).
2 hosted libraries: @tiptap/core, leaflet
```

The last line names the libraries the `<ThirdParty>` boundaries host, each once, so the components
an application takes from elsewhere are a known list. It holds only names a boundary writes out. A
boundary with no `library`, an empty one or a computed one names no library, so it adds nothing to
the list: a placeholder or an expression's text there would read as a hosted package.

The inventory reads what a boundary declares and does not read the file's imports. Lint is what
checks the declaration: `no-raw-styles` reports a boundary whose library is not a package the file
imports a binding from. The list is therefore the hosted libraries of a codebase that lint passes.

It also writes the findings as JSON to `exceptions.json` at the repository root. The file is
gitignored, and nothing reads it.

**What fails the gate:** an undeclared deviation, meaning a red rule turned off by a disable comment that
no `<Bespoke>` accounts for. `pnpm inventory` then exits 1. `pnpm gate` runs it after `pnpm lint`. A
disable written inside a string is text about the ladder, not a comment, and is ignored. A childless
`<Bespoke />` covers nothing, so a disable beside it is still undeclared. So is a disable inside a
`<ThirdParty>`, which accounts for none.

A `<ThirdParty>` that writes no `library` out fails the gate too. It hosts nothing and lint reports
it, so the inventory lists it with no rung, and `pnpm inventory` exits 1 and names the fix. A
declared exception is one a reviewer can read, and a boundary that names no library declares
nothing.

Declared exceptions never fail. If a build failed on rung 4, people would go back to the disable
comment that the rung replaces. What matters in the inventory is its size and its trend. A handful
of declared exceptions is healthy. A growing list means the vocabulary is missing something.

`packages/rules/src/inventory.test.ts` asserts the exact exceptions this repository declares, by
rung, kind and file, so adding one requires a deliberate edit to that test.

## The workbench harness

`apps/*/src/harness/**` holds the tools used to inspect the system, such as the toolbar and the
token gallery that draws swatches in arbitrary resolved colours. It is not part of the product. It
is exempt from every ESLint red rule and from the inventory, and it is the only place under `apps/`
where a stylesheet may exist. The CSS motion law still applies to it. Relay and the page exemplars
get no exemption. The glob is written in `eslint.config.ts`, `packages/rules/src/inventory.js` and
`packages/rules/src/repo-laws.test.ts`, so widening it takes deliberate edits in all three.
`apps/workbench/src/harness/README.md` explains it.
