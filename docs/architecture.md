# Architecture

How the repository is laid out, how the packages depend on each other, and how a design
decision travels from a JSON file to pixels. For the ideas behind it, read
[concepts.md](concepts.md) first.

## Layout

Every package and platform, with what it depends on in the workspace and the name it is
published under. A package with no published name is internal: the repository's own tools,
run from a checkout. The CLI, the MCP server and what they run are also published inside one
package, `@metamorph-labs/polymorph` (`packages/tools`).

## Package graph

A member in `react-ui` imports nothing from the repository except `@polymorph/react`,
`@polymorph/react/motion`, its sibling members and its recipe from `@polymorph/recipes`. It
reaches the engine through `@polymorph/react`, and `react-ui` lists `@polymorph/engine` only as a
dev dependency, for its tests. This makes a member vendorable: a member copied into another
repository still resolves its imports. `polymorph add` copies the recipe beside the member and
rewrites that one import to the relative path, so a vendoring consumer does not install
`@polymorph/recipes`. A vendored copy may also import `@polymorph/engine`, which the consumer
installs. The `vendorable-imports` red rule enforces the boundary and allows that import. A
generated member in another framework imports its own foundation the same way, and
`polymorph add --framework <name>` vendors it the same way.

A recipe has no framework code, so it lives in its own package and not in any vocabulary.
Every web framework's member imports the same file and renders the same class names.
Outside `packages/engine`, only the repository's own tools import `@polymorph/theme`. A consumer
never installs it, because the engine re-exports all of it.

The native packages depend on nothing in the workspace at build time. Their token sources and
contracts are generated from the engine and `packages/native` and committed, so a Swift or
Gradle build needs no Node.

## From a decision to pixels

```
design/systems/<name>.json ─┐
                            ├─► parseSystem / parsePalette        (packages/theme, zod schemas)
design/palettes/<name>.json ┘          │
                                       ▼
                               composeTheme → resolveTheme         axes + seeds → OKLCH ramps
                                       │                           → roles → every token
                                       ▼
                               laws: contrast, coherence, …        refuses an unlawful pairing
                                       │
                                       ▼
                               emitThemeCSS / emitThemesCSS        one CSS block per pairing,
                                       │                           scoped by [data-system][data-palette]
                                       ▼
                               polymorphTheme (build time)         compiled to CSS files; a law fault
                               or polymorph add (install time)     stops the build or the install.
                                       │                           Run time: admitTheme + installThemeCSS
                                       ▼
                               setSystem / setPalette / setMode    @polymorph/engine/runtime: an
                                       │                           attribute swap on <html>,
                                       │                           resolved before first paint
                                       ▼
           packages/recipes read --pm-* tokens only  ───►  pixels
```

A guest system (one that is not in `design/`) takes the same path. The plugin and the CLI admit it
with `admitTheme`, which returns either the CSS or the faults. A theme known only at run time is
admitted the same way in the browser. See [theming.md](theming.md).

Motion takes the same route, from `design/motion/motion.json` into `@polymorph/engine/motion`,
which each web foundation's presence components play (`@polymorph/react/motion` and its
counterparts). Icon roles go from `design/icons.json` into the role data in `@polymorph/engine`
and each web foundation's icon gateway.

The native packages take the same resolved pairing in another form:

```
resolveTheme ──► emitSwift / emitKotlin / emitDart     each default pairing as values, written by
       │                                               pnpm emit:native into each native package's
       │                                               generated directory and committed
       └──────► emitTokenDocument (JSON)               a pairing a server admits at run time, which
                                                        an iOS app reads with PMTheme(tokenDocument:)

registry ──► pnpm native:contracts ──► PM<Member>Props, PM<Member>Rendering, PMIconRole (SF Symbols,
                                       Material Symbols), PMStrings, PMRecipe, in Swift and Kotlin
                                                 │
                                                 ▼
             SwiftUI and Compose members read every value from the PMTheme in their environment
```

A native member reads colours, type, lengths, radii and motion from the theme it finds at its root
(`.pmTheme(_:)` in SwiftUI, `ProvidePMTheme` in Compose), and draws icons through the role's SF
Symbol or Material Symbol. [native.md](native.md) has the native side; [theming.md](theming.md)
has the token document.

## How code is shipped

- **Source in the repository.** Every package's `exports` points at TypeScript source, so the
  apps, the tests and a product that links a checkout compile it directly.
- **Built for the registry.** `@polymorph/engine`, `@polymorph/rules`, `@polymorph/react`,
  `@polymorph/react-ui`, `@polymorph/vue` and `@polymorph/vue-ui` have a Vite library build
  (`pnpm build:packages`), which `publishConfig.exports` points at. The Vue packages' builds
  compile their single-file components, and `vue-ui`'s compiles each member's recipe beside it as
  `react-ui`'s does. It contains ES modules, one per source module (so `'use client'` survives and unused
  members tree-shake), type declarations, and extracted CSS. The `react-ui` build compiles each
  member's recipe from `@polymorph/recipes` into the member's directory, and each module imports
  its own stylesheet. `react` keeps its single stylesheet (the icon gateway's) out of its modules
  so that plain Node can import them. The engine bundles `theme`, including its declarations, and
  ships no CSS. React and every other dependency stay external.
- **Built as source for Svelte.** `@polymorph/svelte` and `@polymorph/svelte-ui` publish their
  components as source, because the consumer's Svelte compiles a component for the browser and for
  a server render, each its own way. Their build (`packages/svelte/scripts/package.mjs`) writes the
  components as they are, the TypeScript modules as JavaScript and the declarations, and each
  member imports its recipe from `@polymorph/recipes`, which the consumer's bundler compiles.
- **Built twice for Solid, and shipped as source too.** `@polymorph/solid` and
  `@polymorph/solid-ui` compile their JSX once for a browser (`dist/`, the `browser` and `import`
  conditions), where `solid-ui` compiles each member's recipe beside it as `react-ui` does, and once
  for a server (`dist/server/`, the `node` condition), which renders to strings and imports no
  stylesheet, so plain Node loads it. `solid` keeps its stylesheet out of its modules, as `react`
  does, and `solid-ui`'s entry imports it. Under the `solid` condition each ships its source with
  the types removed and the JSX kept (`dist/source/`), which an application's Solid compiler reads
  first and compiles for the browser, a server render or hydration.
- **Partially compiled for Angular.** `@polymorph/angular` and `@polymorph/angular-ui` ship the
  Angular package format's partial declarations, written by `ngc` in partial mode and bundled
  into one flat module per entry point under `dist/fesm2022/`
  (`packages/angular/scripts/package.mjs`), which the application's Angular CLI, or Analog's Vite
  plugin, links to the Angular it runs. The CLI compiles no stylesheet a module imports, so the build compiles each
  recipe a member imports, and the recipes it composes from, into the member's component `styles`,
  which Angular adds to the page once, when a member that uses them first renders. The base layer
  ships as `@polymorph/angular-ui/base.css`, which an application lists among its global styles.
  Nothing imports a stylesheet, so plain Node loads every module.
- **Built for a page with no build.** `@polymorph/elements-ui`'s build writes `dist/cdn/`, the
  files a page loads the elements from: `polymorph.js`, which defines every tag and loads each
  member's chunk the first time one of its elements connects, the chunks, `polymorph-all.js`,
  `polymorph.css` with the base layer and every recipe, `prepaint.js` and `themes/<system>.css`.
  No public URL serves them, because the registry is restricted, so `polymorph init --framework
  elements` copies them into an app.
- **Built with nothing external.** `@polymorph/screen`'s build inlines the pure modules of
  `@polymorph/spec` and `@polymorph/registry` it imports, their declarations included, as the
  engine's inlines `@polymorph/theme`, so the package has no runtime dependency. Each subpath is
  an entry of its own, and the vocabulary table is a chunk only the entries that read it load.
- **Built with the files it reads.** `@polymorph/tools`'s build (`packages/tools/scripts/build.mjs`)
  bundles the CLI, the MCP server, the screen emitter and the internal packages they run, and
  keeps every module at its source path below `dist/`. Beside them it writes the registry of the
  tree it ran in, copies every file the registry names and the elements' no-build files at their
  paths, and writes the screen page the workbench builds. `dist/` is therefore a slice of the
  repository, and it is the source root the published CLI and server read, as a checkout is in a
  checkout. Third-party packages stay dependencies.
- **Published as source.** `@polymorph/recipes` has no build. Its `exports` map names
  `./base.css` and `./*.module.css` under `src/`, and the package ships those files as they are.
  The bundler that imports a recipe compiles it.
- **Themes are compiled before they ship.** `@polymorph/engine/vite` and a CLI theme install run
  the theme engine when the application builds or installs. The browser receives CSS and
  `@polymorph/engine/runtime`'s attribute setters, and none of the theme engine's derivation code
  (no zod, no culori). Runtime admission exists for themes that no build can know about, and it
  costs the size of that derivation code.
- **Size is a gate.** `pnpm size` (`scripts/size.mjs`) builds fixture apps against the published
  builds, with the theme compiled the way an application compiles it. It fails when a fixture ships
  more gzipped JavaScript or CSS than its ceiling in `scripts/size/budgets.json`. See
  [verification.md](verification.md#size-budgets).
- **Published to GitHub Packages** by `pnpm publish:packages`, under the names in the
  [layout table](#layout). The rename applies only at the registry. Consumers install the
  packages under their `@polymorph/*` names. See [consuming.md](consuming.md). The packages with
  no published name are internal.
- **Shipped with the repository.** `platforms/ios`, `platforms/android` and `platforms/dart` are
  not uploaded to a registry. An iOS app adds the Swift package by this repository's URL, through
  the root `Package.swift`, an Android app depends on the library JitPack builds from a release
  tag (`jitpack.yml`) or includes the Gradle build from a checkout or a git submodule of this
  repository, and a Dart app adds its package by path or by git. Their version is the release's: SwiftPM reads it from the
  tag, and `pnpm version-packages` writes it into the Gradle and Dart manifests
  ([`.changeset/README.md`](../.changeset/README.md)). Every app builds them from source, so their
  generated sources are committed.
- **Versions.** Every published package follows semver, so a breaking change is a major
  release. Every package carries one version, the release's, in its `package.json`, and the
  release tag is `v` and that version. Changesets (`.changeset/`) records
  each versionable change, `pnpm changeset` adds one, and
  [`.changeset/README.md`](../.changeset/README.md) says which bump a change takes and how to see
  the version the next release gives each package.

## Founding technical decisions

| Decision | Choice |
| --- | --- |
| Layers | The decision layer (the engine, the specs, the laws, the tools) is separate from the renderers. Each renderer draws the same vocabulary from the same tokens. |
| Web runtime | React 19, Vue 3, Svelte 5, Solid 1.9 and Angular 22, and custom elements in the light DOM over the Solid members for a page written in HTML, over an engine with no framework in it. CSS custom properties are the theme contract. The platform provides scoped tokens and runtime theme switching. Themes compile to CSS at build time. |
| Native runtime | SwiftUI on iOS 17 and macOS 14, and Jetpack Compose through Compose Multiplatform (`jvm` and `android` targets). A native member wraps the platform's own control and applies the tokens to it; it does not copy the web's pixels. Flutter has the tokens only. |
| Behaviour | Borrowed: React Aria and Radix primitives provide keyboard, focus and ARIA behaviour in React, and Zag machines in Vue, Svelte, Solid and Angular (through the Angular foundation's own adapter, because Zag ships none) and in the elements, which render the Solid members; the conformance law holds every web renderer to the specs' contracts. SwiftUI and Compose members use the platform's controls. Everything perceivable (styling, motion, API) is polymorph's own. |
| Generation | The Vue, Svelte, Solid and Angular members are generated from one description per member, so the renderers cannot drift apart by hand. The elements are generated as definitions over the Solid members, so they add no anatomy of their own. The native members are written by hand, against generated contracts, because each wraps a different platform control. |
| Colour | OKLCH ramps generated from seeds; light and dark re-derived from one pairing; contrast checked for every lawful text/surface pair. |
| Motion | State-bound transitions in CSS. Springs and exit choreography run on the browser's Web Animations API, through the motion engine inside the vocabulary, and are never exposed to application code. No animation library. Native members read the same motion tokens. |
| Distribution | Open code: web members can be vendored (you own the copy) or linked (read-only package). Consumers get the red rules either way. The native packages are reached at a release tag: by URL on iOS, through JitPack or a checkout on Android, by path or git in Dart. |
| Screen format | Declarative JSON, validated against the registry and emitted for any web framework, or for SwiftUI or Compose when the spec names its platform — not a subset of any framework's syntax. |
| Tooling | pnpm workspaces, TypeScript, Vite, Vitest (node for logic, real browsers via Playwright for components), ESLint + Stylelint + Prettier; SwiftPM and Xcode for iOS; Gradle, Kotlin and a JDK for Android. Node 24 (`.node-version`), the `engines` floor. |
